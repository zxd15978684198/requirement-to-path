# evals/ —— 任务级评测（官方 Skill 清单第 19 条）

这三份是**任务级**评测（不是单元测试）：每条给一个真实用户请求 + 期望行为清单，
判分方式是「让一个装了本 skill 的 agent 跑这条 `query`，再逐条对 `expected_behavior` 打勾」。

格式取自官方 Skill 检查清单所依据的评测写法（`skills` / `query` / `files` / `expected_behavior`）。
`skills` 字段声明本用例需要加载的 skill；`files` 是评测时提供给 agent 的输入文件（相对路径）。

## 怎么跑

```
对每个 evals/*.json：
  1. 起一个干净会话，加载 skills 里声明的 skill（不要把本 skill 的 SKILL.md 直接贴给 agent）
  2. 把 files 里的文件放到 agent 能读到的位置，然后把 query 原样发给它
  3. 拿到产出后，逐条对 expected_behavior 打勾（每条要么过、要么不过，不评"部分完成"）
  4. 记录：通过条数 / 总条数、失败项、以及 agent 是否真跑了 references/self_check.py
```

## 可复核的那一半：`evals/harness.py`（v1.49.0）

上面第 3 步「逐条打勾」原本纯人工，现在把**能机械判的部分**固化成谓词。它不评测 agent（那要起干净会话），
它评测**一份真实产出物**是否满足 `expected_behavior`：

```bash
python evals/harness.py --case 02 --doc <产出物.md> --root <该项目根>
# 每条输出 PASS/FAIL + 引用产出原文当证据；末行给「机械可判 n/6」
```

六条谓词对应 `02-state-persistence.json` 的六条期望：①`文件:行` 取证在项目内真能定位且行号不越界
②出现 `[待确认]` ③同一行同时提「权限」与「绕过/边界/过滤」④有查上游 `libs/` 或「官方实现」的痕迹
⑤0–9 节齐且贴了退出码 ⑥声明只读。

**实测（2026-10 那次真实运行留下的两份产出物，非本轮为凑分而新写；原始评述见 `references/verification-log.md`）**：

```bash
python evals/harness.py --case 02 --doc "<产出物>" --root "E:\projects\某项目"
```

`--root` 必须指向**需求方项目根**，否则①会全判 FAIL：产出物里的 `agent_api.py:88` 是相对模块目录写的，
不传 root 就只能按同名文件在你当前目录里找。同一份文档不带 `--root` 是 2/6、带上才是 3/6——
**分数必须连命令一起记**，否则下一次复现不出来（这一点是复核时当场发现的）。

| 产出物 | 得分 | 未过项 |
| --- | --- | --- |
| `docs/状态信息持久化实现参考.md`（eval 02 那次运行的真产出） | **3/6** | ②无 `[待确认]`（口头信息未与代码对账）③全文未提权限绕过 ⑤跑了自检但没贴退出码 |
| `docs/状态持久化升级计划.md` | **3/6** | 同上三类 |
| 对照：`CLAUDE.md`（普通项目文档） | 0/6 | 说明谓词不是见谁都给分 |
| 对照：本 skill 自己的 E2E 交付物（不同需求的文档） | 1/6 | 需求不同，02 的谓词本就不适用——这是**应然**结果，也说明 harness 只对同需求产出物有意义 |

**它判不了什么（如实写在代码注释里）**：判断"D1 这条决策是否真被论证"、"证据是否语义相关"、
"候选是否真的覆盖了上游"——这些只有人/评审 agent 能判。所以 harness 的分数是**下界**，不是总分。

## 用例

| 文件 | 场景 | 来源 | 实跑过吗 | harness 可判 |
| --- | --- | --- | --- | --- |
| `01-semantic-cache.json` | 给内部问答机器人加语义缓存（近似问题不串答案） | 2026-10 真实运行（真调 github 连接器） | 是（并暴露了"只看前 5 条漏掉 81★ 仓库"的真实缺陷） | **谓词已就绪（7 条 `c1_*`，v1.55.0）**；正例夹具 7/7、跨需求 4/7。**分数以真实产出物 `.eval/e2e-*-semantic-cache.md` 是否存在为准**——谓词就绪 ≠ 有分数 |
| `02-state-persistence.json` | 为多 Agent 项目做状态持久化升级 | 2026-10 真实运行（只读本地代码 + 真调连接器） | 是 | **是，3/6** |
| `03-vague-platform.json` | 极模糊的平台级需求 | 我构造的压力用例 | 本轮起独立会话实跑，产出物直接落在 `.eval/e2e-2026-10-18-vague-platform.md`（**有无分数以该文件是否存在为准**） | **是，6/6**（v1.53.0 首次；**同时 self_check 判 exit 1**，两口径不同，见「诚实边界」） |

`03` 的六条谓词（`c3_*`）：①先澄清后搜／需求方不可达时明说降级 ②框架类候选被标「排除」
③组合型拆分给出依据 ④发现路径不是无范围 `search_code` 且记录了命中数 ⑤0 候选降级级别明示
⑥未解项 + 下一步 + 自检退出码。

`01` 的七条谓词（`c1_*`）盯的是**取证质量**而不是流程骨架（那是 03 的事）：①先判适用性、不跳到方案
②门禁 1 的澄清落成 `L0-P*/L0-C*/L0-S*` 编号产出物 ③直搜（`search_repositories` + `stars:` 下限）且
**取回条数 ≥ 命中数**（或写明已换词／分页看完）④候选集含 GPTCache 之外至少一个，且每个候选**附近**
（±3 行）写出「抄它会在什么条件下坏」⑤取证是 `repo/<owner>/<name>:<path>#符号`／`:L行`，
不许裸行号、不许拿 README 当结论 ⑥0–9 节 + 跑过 self_check ⑦只读。

`01` 正例夹具 `.eval/fixtures/case01_good.md` 只 1977 字符，写它的过程当场抓出**两处「把禁用写法当成用法」**
的假阳性（同族错误第三次出现）：③把标题里「未用无范围 `search_code`」判成"用了"，⑤把「也不拿 README 当结论」
判成"拿 README 当结论"。修法是给否定词表补 `未用|没用|不拿|不当|而非`——**判据必须能读否定**，
这和 v1.53.0 在 self_check 里修「未分页看完被当成已分页」是同一个病。

**谓词本身也要受检**（否则「永远判 FAIL」会显得比谁都严）。`audit.py` 第 8 组就是这件事：

```bash
python .eval/audit.py   # 第 8 组：01/03 正例夹具必须满分（7/7、6/6）、跨需求反例必须低分、缺产出物与未实现用例必须 exit 64
```

正例夹具 `.eval/fixtures/case03_good.md` 是**手工合成**的，不含任何真实发现——它只证明谓词能过。
写它的过程抓出了 ④ 的三次误判（详见 `references/verification-log.md` v1.50.0 行）：把「结果」当关键词、
把「返回」+任意数字当计数、把数据库语境里的「命中」当检索命中。**同一个词在本 skill 的领域里就有两种含义**，
这是关键词判据的固有风险，也是为什么每条谓词旁边都写了它踩过什么。

## 诚实边界

- 01/02 的 `expected_behavior` 是从**已经发生过的那次运行**里提炼的：它能验证"下次是否还犯同样的错"，
  但它**不能证明** skill 在全新需求上也有效。
- 03 **首次有分数了：6/6**（v1.53.0，产出物 `.eval/e2e-2026-10-18-vague-platform.md`，由独立子代理按 SKILL.md 实跑）。
  但同一份产出物在 `self_check.py` 下是 **exit 1**——两条口径不冲突，它们量的是不同东西：
  harness 判「行为是否发生」（先澄清再搜、框架被排除、降级级别明示、贴了退出码），
  self_check 判「形式是否合规」（候选发现表里 `取回 20 < 命中 54` 且没换词 = 「只取前 N 条」的形式缺陷）。
  **两个分数必须一起看**：6/6 说的是"该做的动作都做了"，exit 1 说的是"其中一步的取证方式不合格"。
- 这份 03 产出物还顺带抓出了**自检脚本自己的一个假绿**：`R3-2` 行写的是「**未**完成：既**未分页看完**」，
  而豁免正则 `已换词|已分页|分页看完` 匹配到被否定的那句 → 真实缺陷被静默放过、原 `exit 0`。
  v1.53.0 修好否定式判读后，同一份文档从 exit 0 变成 exit 1，缺陷才浮出来。**这就是"跑真需求"换来的东西**。
- 01 的谓词（v1.55.0）**已就绪但没有分数**：正例夹具 7/7 只证明判据能过，跨需求 4/7 只证明它不对谁都给分；
  真实产出物必须由一次实跑产生，落在 `.eval/e2e-*-semantic-cache.md` 之后 `--case 01` 才有意义。
  `--case 09`（不存在的用例）仍 exit 64 并说"未实现，不等于通过"——**未实现要能被读懂成"未实现"，不是"跑失败"**
  （v1.55.0 修：先判有无谓词再读用例文件，否则"找不到用例文件 exit 1"会伪装成一次失败的运行）。
- **03 的子代理还回报了 8 条「skill 指令不清楚/矛盾」**（v1.53.1 逐条核实）：5 条是文档真缺陷、1 条是它自己的检查器假阴性（v1.53.0 已修）、2 条是措辞重叠。最要紧的一条：分类表把「框架」与「平台/产品」**双双判 ❌**，于是"做一个平台"这类需求在规则层面**永远不可能有整块对标**——降级从兜底变成了必由之路。这类缺陷机检查不出（检查面 #22），只有"让另一个 agent 按文档真跑一遍"才会浮出来。**所以每版本至少一次真跑，不能只跑 audit。**
- 评测集本身也需要版本化：改 SKILL.md 的判据后，`expected_behavior` 要跟着复核，否则它测的是旧行为。
- 哪条判据压根没被覆盖、为什么没覆盖，统一记在 `.eval/SURFACES.md`（21 条检查面，其中 5 条明写「无覆盖」）。
  这张表是"还有哪里没查"的唯一答案来源——比任何口头承诺可靠，且由 `audit.py` 第 10 组反伪（全绿篡改、删行洗白都判红）；`audit.py` 现有 12 组。
