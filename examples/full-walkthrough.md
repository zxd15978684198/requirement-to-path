## 样例 A：向量库增量同步（v1.3 实测，完整流程）

### 0. 需求从哪来（L0 问答精华）

**原始需求（一句话）**：把本地资料库的变化同步到向量库，别每次全量重建。

| 门禁 | 关键问答（节选） | 产出 |
| --- | --- | --- |
| 门 1 痛点与约束 | 现状：手工跑脚本全量重建；最烦：一次几十分钟且重复写入；频率：每周几次；技术栈 Python + Chroma | 痛点清单 3 条 |
| 门 2 方案选择 | 用需求方语言问："可见范围改了但正文没改，你希不希望它为此重新算一遍？" → 答：不希望 | 选「metadata 变化只更新元数据，不重算向量」 |
| 门 3 需求规格 | 明确不做：不做多租户、不做 UI；验收：重复跑不产生重复写入 | 规格含 2 条 `[假设]` |

**一致性检查发现 1 处矛盾**：数据来源答「分页接口（拿不到完整清单）」+ 删除策略答「自动删」——危险组合，提交用户裁决后改为「先预览再删」。

> **两条交互实测教训**（已回写进 SKILL.md / l0）：
> ① 门 2 第一版用方案语言提问（"权限变化时重算向量是浪费吗？"），用户答「我不太明白什么意思」→ 改用需求方语言后正常作答；
> ② 门禁 1 的「现在怎么绕」列曾被需求方**连续两次**读成"你在提的方案"→ 呈现清单时须显式声明"右两列描述的是现状，不是提案"。

### 1. 最终设计决策表（门禁 4 收敛产物）

| # | 裁决项 | 结论 | 来源 |
| --- | --- | --- | --- |
| 1 | 变更识别粒度 | 块级（content hash 对比） | L2 代码事实 |
| 2 | 删除策略 | 先预览再删（dry_run），不做静默删除 | 门禁 3 矛盾裁决 |
| 3 | 失败安全 | 扫描不完整时**禁止**任何删除动作 | L2 发现的坑（见下） |
| 4 | 元数据变更 | 只 patch metadata，不触发重嵌 | 门禁 2 裁决 |
| 5 | 存储适配 | 仅用 upsert，禁用 insert 冒充 | L2 语义误用实例 |

### 2. 对标结论

- **类型判定教训（实测）**：前两轮搜索**全部命中框架**，被用户连续纠正两次「不要框架要模块」→ 此后补上「README 第一句能否用『它做 X』概括」的硬判据；
- **技术栈教训（实测）**：漏问技术栈那一轮，搜出的 5 个语义缓存候选**全是 JS/Go/Ruby**，无一可用——技术栈必须进 B 组第一题；
- **候选与成熟度** `(压缩)`：社区规模（star）中 / 活跃度（pushed_at）放缓 → 组合结论「高 star + 停滞 → 适合读设计，不建议作生产依赖」；
- **缺口清单比匹配分数重要**：目标存储兼容 ❌、删除预览 ❌ → 这两项就是自己必须补的活。

### 3. 分步实现路径（三件套节选）

> 完整阶段划分见 `../references/l3-mode-map.md` 的 P0–P8 实例。此处示范两步的写法：

**P0 契约冻结（模式：Spec）**

| 项 | 内容 |
| --- | --- |
| 指令模板 | "定义 Document 身份规则、台账表结构与适配器接口签名。**不要**在此步实现任何哈希或存储逻辑。" |
| 通过信号 | 接口签名与台账字段通过评审，身份规则明确到「相对路径 vs 绝对路径」级别 |
| 翻车信号 | 出现"先写着看"的字段 → 停下，回 Spec（身份不稳会导致全库重算，见 L2 实例） |

**P3 存储适配器 + Mock（模式：TDD）**

| 项 | 内容 |
| --- | --- |
| 指令模板 | "实现 Adapter，提供 upsert_many / patch / delete。**不要**调用真实向量库，用记录调用的 Mock 测试。" |
| 通过信号 | `assert len(mock.upsert_calls) == 0`（metadata-only 场景不该触发重写）通过 |
| 翻车信号 | 出现 `insert` 冒充 upsert 的写法（重复 ID 会失败）→ 立即纠正语义 |

### 4. 验收清单（节选，含防护性验收）

| # | 验收项 | 可观察证据 | 类型 |
| --- | --- | --- | --- |
| 1 | metadata 变更不重嵌 | `mock.upsert_calls == []` 且 `mock.patch_calls` 非空 | 防护性 |
| 2 | 扫描不完整时不删除 | 注入不完整扫描 → 计划中 delete 数量为 0 | 防护性 |
| 3 | 重复执行幂等 | 同输入连跑两次，第二次无写入动作 | 防护性 |
| 4 | 删除前有预览 | dry_run 输出待删清单且未实际删除 | 功能 |

### 5. 已知限制

- 对标模块的 12 条测试**完全没覆盖三条安全边界**（扫描完整性、空文本误判、单文件异常隔离）→ 自己按上表补防护性验收；
- 本路径未做多租户与并发保护（已在需求规格中明确"不做"）。

## 样例 B：竖排古籍→横排 + 标点 + 坐标对照（v1.5 实测，组合型 + 降级链）

### 0. 判形状（漏斗第 0 步）

需求描述超过三句、且含多个环节 → **判定为组合型任务**（若按整块匹配搜，实测 0 命中）。

**拆解结果**：OCR / 文字识别 + 古文标点断句 + 版面坐标对照 = 3 个子机制。

### 1. 逐子机制搜（v1.5 实测结果）

| 子机制 | 整块匹配结果 | 拆分后命中 | 备注 |
| --- | --- | --- | --- |
| 竖排古籍 OCR | **0** | ndlocr-lite（1327★） | **跨语言参考**（日文古籍模型），实现不可直接照抄 |
| 古文标点 | **0** | guwen-punc | 模型型组件，GitHub 搜码漏召回，是借道引用它的代码才发现的 |
| 坐标对照 | **0** | `(压缩)` 未单独解决 | 缺口清单中标注"无对标" |

### 2. 降级链走到哪一级

- ① 部分匹配：**走通**（子机制逐个搜，命中 2/3）；
- ② 跨语言 / 跨栈设计参考：**走通**（ndlocr-lite 标注"仅设计参考"）；
- ③ 退回 `spec-development`：未触发；
- ④ 明示无先例：未触发（但坐标对照子机制接近此级，产出物需标注风险）。

### 3. 本样例暴露的已知限制（模型型组件盲区 → 已由 HF 第二搜索面覆盖）

**模型型组件（如 guwen-punc）不在 GitHub 搜码的召回范围内**——它没有"被大量代码引用"的痕迹。
本样例（v1.5）当时的发现路径是"先找到引用它的代码，再反向发现它"。

**该盲区已在后续版本补上**：模型型组件改走 HuggingFace 第二搜索面（做法见 SKILL.md「模型型组件的第二搜索面（HuggingFace）」，做法是补充而非替代 GitHub 漏斗）；账本 v1.26.0 记该面首次跑通——官方域名不可达，**须走镜像 `hf-mirror.com`**。

**仍未解决的只剩环境依赖**：HF 面依赖镜像可用性（镜像是第三方服务）。镜像不可用时，"核心是一个模型"的需求回到盲区，**须如实告知用户，不要硬凑对标**。
