## 一、流程图（原文）

```
L0 需求澄清 ──┬─ 门禁 1 痛点清单确认
              ├─ 门禁 2 方案选择（触发 L1 搜索）
              └─ 门禁 3 需求规格确认
                     ↓
L1 定位       L1.0 加载 github 连接器 → 漏斗七步（第 0 步先判需求形状：整块 / 组合型）
              关键词构造 → 捞候选（1-A 直搜发现 / 1-B 反查核实）→ 结果分类 → 匹配矩阵
                                    → 成熟度 → 代码验证 → 交付
                     ↓
L2 提取       读码规程：入口 → 数据结构 → 接口契约 → 测试
                     ↓
              门禁 4 对标裁决（优缺点三分类 + 逐项征询）
                     ↓
L3 路径重构   分步实现路径（每步三件套 + 开发模式标注）
```

## 二、执行序列（11 步，原文表；原表曾被打断，此处已复原为完整表）

| # | 阶段 | 输入 | 做什么 | 产出 |
|:---:|---|---|---|---|
| 1 | 适用性判断 | 需求原话或材料 | 判四类分流：模糊→走本流程／已明确→转 `spec-development`／只想压测→转 `grill-me`／预判无对标→**开工前就告知**，直接走 0 候选降级③/④（不先耗搜索轮次）。**并先看现状**：在被改造的项目里 grep 一遍这件能力是不是**已经有了**（表／字段／函数／配置／迁移记录／既有测试），**已经有就改成回答「现有实现与需求的差距在哪」**，而不是从零规划（实测代价见 `references/verification-log.md` v1.58.0 行） | 走／不走的结论（不走则给出目标 skill）＋**现有实现的坐标与差距**（若已有） |
| 2 | L0 门禁 1 | 需求原话 + `l0-question-bank` 按域选题 | 问现状与痛点、量级与约束、边界与失败 | 痛点清单（编号 `L0-P<n>`）+ 约束清单（`L0-C<n>`） |
| 3 | L1.0 接通 | — | 加载 `github` 连接器 → **本次将用到的每个工具各探活一次** → 判全通／半通／全断 | 工具面状态 + 探活记录 |
| 4 | L1 半程 | 门禁 1 的痛点清单 | 只找"候选做法"供门禁 2 当选项（不追完整对标） | 方案选项表（每项带代价与对标证据） |
| 5 | L0 门禁 2 | 步骤 4 的选项表 | 逐机制维度**分别**征询（正交维度不许合并成一问） | 方案决策表（`L0-D<n>`） |
| 6 | L0 门禁 3 | 门禁 1 + 门禁 2 产出 | 收敛"做什么／明确不做什么／验收标准／约束前提"，技术选型必须在此闭合 | 需求规格（`L0-S<n>`）+ `[假设]` 清单（`H<n>`） |
| 7 | L1 全程 | 门禁 3 的规格 | 漏斗七步：判形状 → 关键词 → 直搜捞候选（逐条看完候选表）→ 分类 → 匹配矩阵 → 成熟度 → 代码级验证 | 对标候选集（含逐仓库链接与成熟度）+ 缺口清单 |
| 8 | L2 提取 | 步骤 7 的候选集 | 按固定顺序读码：入口主流程 → 数据结构 → 接口契约 → 测试 | 事实表（`[代码可读]`/`[推断]`/`[测试可证]`）+ 坑清单（`K<n>`） |
| 9 | 门禁 4 裁决 | 步骤 8 的事实表 | 优缺点三分类 + 天花板条目逐条征询／打包默认项显式列出 | 最终设计决策表（`R<n>`/`D<n>`） |
| 10 | L3 路径重构 | 门禁 4 的决策表 | 逐步给三件套（指令模板／通过信号／翻车信号）+ 开发模式；每步带来源列 | 交付文档（第 0–9 节结构，见「文档结构」表） |
| 11 | 交付前自检 | 步骤 10 的交付文档 | 逐项核对自检清单五组 + **第 8 条引用关系矩阵逐对核验** | 全绿才可交付；未过则回补对应章节 |
