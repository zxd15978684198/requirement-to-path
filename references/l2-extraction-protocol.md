## 一、读取顺序（不读全仓）

```
1. 入口主流程      engine.py / sync() / main() —— 看清整体步骤顺序
2. 数据结构        台账表结构 / 数据模型 / dataclass —— 看清字段与语义
3. 接口契约        适配器 / 抽象基类 —— 看清扩展点
4. 测试文件        断言即验收清单 —— 看清它验证了什么、没验证什么
```

**体量判断**：代码总量 < 30KB 时可整读；超过则严格按顺序，只读这四处。

### 拿到正文的三条通道（`get_file_contents` 渲染不出时**不许停**）

| 通道 | 形态 | 什么时候用 |
| --- | --- | --- |
| 连接器 `get_file_contents` | 直接回文本 | 客户端能渲染正文时（首选） |
| **GitHub REST `api.github.com`** | `GET /repos/<owner>/<repo>/contents/<path>` → **base64 解码落盘** → 本地 `grep -n` 取行号 | 连接器只回 `successfully downloaded text file (SHA: …)`、或正文位置显示 `[embedded resource unsupported; raw resource data remains available to programmatic callers]` 时**必须切到这条** |
| `search_code`（带 `repo:` 范围 + 符号名） | 返回 `text_matches[].fragment`（片段正文）＋ 每项自带 `sha`（**文件 blob sha**） | 上面两条都拿不到正文时的**最后通道**：能证明"这段代码在"，**给不出行号**，但那个 `sha` 可以满足下方"行号或 blob sha"的最低形态 |

`raw.githubusercontent.com` 常因 TLS/超时不可用（实测 `web_fetch` 打 raw 直接 `fetch failed`，而**同一环境**下 `api.github.com` 可用）→ **不要把 raw 当主通道**。

**两条实测坑（v1.56.21）——通道名对、工具名错：**

- **REST 通道要挑对工具**。`api.github.com` 走**内建 `WebFetch`** 可能直接报
  `multiple usable web providers are registered (deepseek-fetch-api, http); configure one explicitly`
  ——**那不是"没有这个文件"，是那个工具在本机没配好 provider**。同一个 URL 改走 **`fetch` MCP 工具**（`mcp__fetch__fetch`）实测返回完整 JSON：`content` 是 base64、`sha` 是 blob sha、`encoding: "base64"`。**渠道判断错了会把"工具没配好"读成"上游没有这个实现"，直接毁掉 L2 的取证结论**。
- **`read_mcp_resource` 不是通道**。本连接的资源清单只有四个 `ui://github-mcp-server/...`（MCP App 界面），**没有** `repo://{owner}/{repo}/contents{/path*}` 这种模板（`list_mcp_resources(server="github")` 实测）→ 照那个形态调只会得到 `fetch failed`。**不要把它写进流程，也不要据它判断"正文读不到"。**

### 出处的最低形态：行号 + blob sha

**既没有行号、也没有 blob sha 的引用不算取证**——只给"符号名"或"文件路径"都属未取证：
- **行号**：REST 取回正文后本地数（`grep -n`），或 `list_commits(path=…)` 定位最后改动行；
- **blob sha**：`contents` 响应里的 `sha`（文件 blob）或 commit sha，附在结论旁供复核者一键校验。

> 为什么写死这条：同一次任务里，走连接器的那条路只能给"符号名"（正文渲染不出、raw 又不通），走 REST 的那条路给出了**行号 + blob sha**——**取证形态的差别不是风格问题，是可复核与不可复核的差别**。
>
> **落到第三条通道（`search_code` 片段）时这条仍然守得住**：片段给不出行号，但返回项自带**文件 blob sha**，所以"行号或 blob sha"里至少满足后者——引用写成 `repo/<owner>/<name>:<path>#<符号名> @<sha前 8 位>`，并在产出物里如实写明"本环境正文通道不可用，取证形态为片段引用、无行号"。**"拿不到行号"不是"不能取证"，但反过来，"只给符号名却不给 sha"仍是未取证。**

## 二、产出格式

每条结论必须包含三部分，缺一不可：

```markdown
### <结论标题>
- **它怎么做**：<具体做法，含函数名/字段名>
- **与我的方案差在哪**：<相同 / 更好 / 更差 / 它没做>
- **代码位置**：<文件>:<函数或行号区间>
- **标注**：[代码可读] / [推断] / [测试可证]
```

### 三类标注的用法

| 标注 | 含义 | 要求 |
| --- | --- | --- |
| `[代码可读]` | 代码里直接能看到的事实 | 必须给文件位置 |
| `[推断]` | 你的推测（如"它的意图是…"） | **必须给验证方法** |
| `[测试可证]` | 有测试覆盖的行为 | 指出对应测试函数名 |

**禁止把推断写成事实**——这是事后合理化最常见的入口。

## 三、问题类型检查清单

逐类核查对标模块，缺哪类就记哪类：

| 类型 | 检查问题 | 实测实例（来源：向量库增量同步项目） |
| --- | --- | --- |
| **静默数据事故** | 有没有"跑的时候不报错、事后发现丢数据"的路径？ | 无扫描完整性检查 → 目录异常时全库清空 |
| **静默误判** | 某类输入被当成另一种语义处理了吗？ | 空文本文档不进"已见集合" → 被判删除 |
| **中断风险** | 单个元素失败会不会拖垮整体？ | 单文件解析异常未捕获 → 全流程中断 |
| **身份不稳** | 标识依赖什么外部因素？ | doc_id 依赖路径字符串形式（相对/绝对不同即全变） |
| **性能** | 有没有 N 次调用的循环、没有批量的地方？ | 适配器仅支持单条 upsert |
| **语义误用** | API 用的是不是它真正的语义？ | 用 `insert` 冒充 upsert（重复 ID 会失败） |
| **与需求不符** | 它没做但你需求里有的？ | 无删除预览 |

### 优先级

**安全边界类最高**——它们跑的时候不报错、事后才发现，代价最大。

## 四、测试文件的用法

对标模块的测试文件是**现成的验收清单**，直接搬用：

| 做法 | 价值 |
| --- | --- |
| 看它断言了什么 | 直接成为你的验收项 |
| **看它没断言什么** | 找出盲区——实测发现它的 12 条测试完全没覆盖三条安全边界 |
| 借它的 mock 模式 | 用"记录调用次数"的假实现，断言**某个昂贵动作未被调用** |
| 注意"已知限制"的写法 | 成熟做法是把限制写成受测试保护的行为契约（注释标 `known limitation`），而非留白 |

### Mock 断言模式（值得直接照抄）

```python
class MockStore(Adapter):
    def __init__(self):
        self.upsert_calls, self.patch_calls, self.delete_calls = [], [], []

    def upsert_many(self, ids, vectors, metadatas):
        ...
        self.upsert_calls.extend(ids)

# 验收时断言"没有发生什么"，而不是断言结果数量
assert len(mock.upsert_calls) == 0, "该场景不该触发重写"
assert len(mock.patch_calls) > 0,   "应该只发轻量更新"
```

**为什么更强**：直接证明某个昂贵动作**根本没被调用**，且不需要真实外部依赖。

## 六、四步走：读什么、产出什么、什么时候停

| 步 | 读什么 | 输入 | 产出 | 停手条件 |
|:---:|---|---|---|---|
| 1 | **入口主流程**：`engine.py` / `sync()` / `main()` 一类 | 步骤 7 判定的深挖子机制 | 该模块的代码级执行顺序（编号列出） | 能按顺序复述主流程即停 |

| 4 | **测试文件**：断言 + mock 实现 | 步 3 的契约 | ① 直接可搬用的验收项 ② **它没断言什么**（盲区） | 盲区列出即停 |
