# L3 开发模式映射与 skill 推荐

<!-- self_check: genre=reference -->

路径文档里每个施工步骤都要标注开发模式，并推荐配套 skill。

---

## 一、三种模式的判据

| 模式 | 适用判据 | 不适用 |
| --- | --- | --- |
| **TDD（测试先行）** | ①契约明确（输入输出已定）②可独立验证（不需真实外部依赖）③纯逻辑或可用 mock 替代 | 需求仍在变、验证需要真实环境 |
| **Spec（规格驱动）** | ①顺序/边界/取舍需先确认 ②做错了成本高、难回滚 ③涉及多方约定 | 改动微小、契约已稳定 |
| **场景测试（集成）** | ①需要真实文件系统/网络/数据库 ②验证端到端行为 | 单点逻辑（用 TDD 更快） |

### 通用规律（一句话）

> **契约与顺序用 Spec 定，纯逻辑用 TDD 验，涉及真实环境用场景测试。**

---

## 二、阶段 → 模式映射

### 通用模板（按步骤性质对照）

| 步骤性质 | 模式 | 判据 | 典型步骤 |
| --- | --- | --- | --- |
| 定义数据结构 / 接口签名 / 身份规则 | **Spec** | 定了牵连全局，改动成本高 | 契约冻结 |
| 纯函数（哈希、格式化、计算） | **TDD** | 输入输出明确，无副作用 | 工具函数 |
| 带明确契约的类实现 | **TDD** | 可用 mock 独立验证 | 适配器、客户端 |
| 判定逻辑（分类、路由、规则） | **TDD** | 用例可穷举 | 变更判定、状态机 |
| 涉及安全边界的规则 | **Spec** | 错了静默丢数据 | 删除前提、失败语义 |
| 主流程编排 | **Spec + 集成测试** | 顺序即语义 | 主入口 |
| 端到端行为 | **场景测试** | 需真实环境 | 全链路验收 |

### 实例（增量索引同步模块）

> **符号澄清（v1.56.22 补）**：本表的 `P0`–`P8` 是**这个示例模块的施工步骤编号**。它与 `SKILL.md` 里表示**痛点编号**的 `L0-P<n>` **不是一回事**，也**不是**交付文档的 §0–§9 章节号（那是文档结构轴）。同时 `SKILL.md` 里还有个"**P 步骤**"的说法，指的是业务叙事里的阶段。三个轴各自独立，**不要互相套用**——盲跑 5 在这处把三种编号混读过。

| 阶段 | 模式 | 理由 |
| --- | --- | --- |
| P0 契约冻结（身份规则/台账/接口） | **Spec** | 一旦定了牵连全库 |
| P1 哈希与切分工具 | **TDD** | 纯函数 |
| P2 台账读写 | **TDD** | 存取往返可独立验证 |
| P3 存储适配器 + Mock | **TDD** | 契约已定，mock 可独立验证 |
| P4 扫描与变更判定（含安全边界） | **TDD + Spec** | 判定可穷举用例；安全边界要先写清规则 |
| P5 主流程编排 | **Spec + 集成** | 顺序即安全语义 |
| P6 删除预览 dry_run | **Spec** | 错了会误删 |
| P7 报告与统计 | **TDD** | 纯计算 |
| P8 端到端验收 | **场景测试** | 需真实文件系统 |

## 三、相关 skill 推荐

### 按模式推荐

| 模式 / 场景 | 推荐 skill | 说明 |
| --- | --- | --- |
| Spec 驱动 | `spec-development` | 七阶段：搜索→决策→澄清→编写→审批→实施→验证；含一致性与独立审查 |
| 方案压测 | `grill-me` | 逐层拆解已有方案，直到达成共识 |
| 无人值守 TDD 循环 | Superpowers `subagent-driven-development` | 写失败测试→通过→重构→**冷读审查子代理** |
| 跨团队 / 跨工具的可持久规格 | GitHub Spec Kit（`github/spec-kit`） | 工件落盘 + agent-neutral |
| 小改动不想走重流程 | BMAD-METHOD 的 Quick Flow 轨道 | 跳过前置阶段直达实现 |
| 输入校验与健壮性 | `robust-input-validation` | 防御性编程 |
| 教程内嵌代码可运行性 | `tutorial-code-verifier` | 校验 Markdown 教程代码 |
| 高保真原型 | `rapid-prototype-craft` | 快速验证想法 |

### 推荐原则

1. **只推与当前阶段模式匹配的 skill**——不要一次罗列全部，否则用户无从选择；
2. 标注**为什么此时推它**（一句理由）；
3. 本地已装的直接写名字；开源的给出仓库。

## 四、路径文档的结构要求

**章节骨架以 SKILL.md「L3 路径重构 → 文档结构」为唯一来源（0–9 节），此处不重述**——v1.18.3 去重：本文件此前另立过一套 0–5 的六节结构，与 SKILL.md 的编号互相冲突（同一份文档结构被写了两处，改一处忘一处）。

本节只负责**每一步内部**要写什么——三件套与模式标注见下。

**同样不重述的还有**：「业务实现叙事」章的**五段式**（五段的名字与含义见 `SKILL.md` 的「五段式 ＝ ⋯」定义）、来源列的封闭域（`L0-P<n>`／`L0-C<n>`／`L0-D<n>`／`L0-S<n>`，见 `SKILL.md`）、验收清单的四类标记口径——都属 SKILL.md 的射程。本文件只写 L3 每一步内部要写什么。

### 每个步骤的三件套（缺一不可）

| 项 | 内容 | 来源 |
| --- | --- | --- |
| **指令模板** | 可直接复制的提示词，含"明确不要做什么" | 从对标模块的划分反推 |
| **通过信号** | 必须跑出来的输出 | 从对标模块的测试断言反推 |
| **翻车信号** | 出现什么说明走错了 + 处置 | 从 L2 的问题清单反推 |

### 硬约束

**每一步都要能追溯到「L0 的某条裁决」或「L2 的某段代码／某个坑」。**

禁止无来源的步骤——那会把文档退化成"事后合理化"，而不是真实的实现路径。

### 通过信号必须「可判」（施工方回访实证）

> 来源：一份"看着完整、`self_check` 0 violations"的 L3 文档，被交给一个**拿不到仓库、只读文档**的施工方按字面实现——四步里有一步整层缺失、一条契约与另一步互斥。**问题都不在"信息不足"，而在"判据不是谓词"。** 以下五条由那次回访实测反推，写进文档前逐条自查。

| 判据 | 反例（实测踩中） | 改法 |
| --- | --- | --- |
| **① 通过信号必须是可判谓词**：给出量什么、阈值、方向 | 「只增减该 doc 的**块数量级**」——3→4 算过吗？3→40 呢？ | 「其余 doc 块数不变，且 `Δcount == len(chunks_new)`」 |
| **② 每条验收断言必须有生产方**：谁写这个数据、哪一步负责 | C4 断言「`ledger` 总块数 == `collection.count()`」，而 P0/P1 里**没有任何函数写 `ledger.blocks`**、`removed` 的行谁删也没写 | 指到具体步骤（"由编排层在写块成功后统一回写"），否则断言永远不成立 |
| **③ 接口签名必须覆盖需求里的全部类别** | `sync(changed, removed)` 没有 `added` → 新增文档索引 0 块，而**四条通过信号照旧全绿**（静默失败） | 签名从 L0 的分类枚举反推：四类一个不许漏 |
| **④ 步骤之间必须有一层胶水被显式交付** | P0→P3 四步无人交付"算全量指纹 → diff → 分类调 sync → 回写 ledger → 处理 `--full`"这段编排 | 补一步 P-1（前置编排），别指望施工方自己拼 |
| **⑤ 同一操作只给一套机制** | §6 说"按 `doc_id` 前缀可删"、§7 写 `delete(where={"doc_id": d})`，而写块 metadata 用的是 `document_id` → 删除命中 0 且 `DuplicateIdError` | 键名写死在数据契约节，写入与删除共用同一个键 |

**配套两条**：⑥**禁止"取消注释某段现存代码"式指令**——对拿不到仓库的施工方是空指令，交付物必须自足；⑦**两条约束互相排斥时必须二选一并说明为什么做不到另一条**（实测：P1 的"先删后写"与 C2 的"失败后旧块仍在"在 Chroma 上不可兼得，文档同时要求了二者）。

**其中 ①⑤⑥⑦ 已进 `self_check.py` 第 8 项机械检查**（对含「通过信号」列的步骤表：非谓词措辞／`where={"K"}` 的 K 全文未定义／"取消注释…"式空指令／"先删后写"与"旧块仍在"并存，四条判违规）；**②③④ 仍需人工**——它们要判断"这条断言的数据由谁生产"，正则做不到。

### 验收清单的写法

- 每条必须有**可观察的运行证据**（不能是"能用"）；
- 优先纳入**防护性验收**（对"不该发生的事"的断言）——一个模块的质量上限看防护性验收有多少条；
- 对已知限制，**断言当前行为**并注释 `known limitation`，而不是断言理想行为。

### 5.1 业务实现叙事章与模块全景（硬约束 2）

**规格六条**（每条都带实测来历）：

- **字段定义以本章为唯一权威**：本章各阶段的「字段设计」四列表是字段的**唯一定义处**；
  §2 的字段补表**只补类型与必填、逐一对齐，不另行决定有哪些字段**。两处字段名集合必须完全一致
  ——**以减少一处定义的方式消灭漂移，而不是靠事后核对**（实测缺陷：本章定义的字段未进补表）。
  ⚠️ **别把这张补表叫「§2.4 字段表」**：文档结构表的 §2 里没有 2.4 这一节，
  `references/delivery-checklist.md` 曾按「§2.4」写、执行者只能自创一节来对号（实测撞到）；
  引用时写「§2 的字段补表」。
- **五段式 ＝ 场景 → 意图 → 字段决策 → 出口 → 失败处置**（**这五个名字只在本节定义**；
  别处一律写「五段式」并指回这里，不许重述）：
  **场景**＝这个阶段在真实业务里何时发生、由谁触发（拿贯穿样例的具体输入说，不写「用户发起请求」这类抽象话）；
  **意图**＝要达成什么、达成后业务上少哪个痛点（对应 `L0-P<n>`）；
  **字段决策**＝本阶段决定或新增了哪些字段（类型／必填／默认值）＋**为什么是这个取值**
  （对应 `L0-D<n>`／`R<n>`；四列表是字段的唯一定义处）；
  **出口**＝交给下一阶段的确定状态（＝下一阶段的输入前提）；
  **失败处置**＝失败或数据不合法时发生什么（拒绝／回滚／标记待处理）＋靠什么恢复。
  **三段式 ＝ 场景 ＋ 意图 ＋ 出口**——就是五段式去掉「字段决策」与「失败处置」，**名字与顺序不变**。
  （v1.56.22 补：此前全文只泄露了「场景／意图／出口」三个名字，另外两段从未命名，盲跑 5 只能自拟；
  一条勾选项级的硬要求却查无定义。）
- **按阶段数分档**（体量花在真要做决策的地方，不平均用力）：**阶段数 ≤4** 时每个阶段都写完整五段式；
  **阶段数 ≥5** 时只对「有字段决策」的核心阶段用五段式，其余阶段压成三段式。
  判断依据是「这个阶段要不要做决策」，不是「这个阶段重不重要」。
- **一份贯穿样例从头穿到尾**：选一份有代表性的输入（实测用一份制度文档），阶段三、四、七等关键处都拿它举例，
  最后用「同一份文档的两次版本迭代」收尾（首入库 + 改一处 → 差异输出）。
- **业务诉求 → 阶段 → 字段 → 决策 全表**（**阶段数 ≥5 时才生成**，当索引用；阶段少时各阶段已说清映射，
  生成即重复）：把业务视角与技术决策双向索引起来，需求方看业务侧、施工者看决策侧。
- **位置在决策表之前**（第 1 节）：先让读者建立整体印象，再看证据与代价。
  实测该章 258 行、覆盖九阶段后，需求方评价「有助于理解整体模块的实现」。

**反面形态（实测被退回）**：把业务视角压成「每步 3 行的八步摘要」塞在技术章中间
——用户会读成「单拎出来一小部分」，不认。

**模块全景先行**：实现路径前必须先让读者看到「要实现的是一个什么样的模块」——
一句话定义 + 数据流图 + 做什么/不做什么边界表 + P 步骤如何拼装成模块（消除碎片感）。
**图的设计原则**：模块数据流图用 `flowchart TD`（上下布局）+ 单行节点文字 + `subgraph` 分阶段
（输入／核心／输出／消费方）；**skill 执行流程图不进交付文档**（那是账本职责）。

### 5.2 数字、公式与术语（硬约束 4）

**标记口径**：**估算类数字**（成本／耗时／规模／收益／占比）必须属于
`[实测]`（写明测量条件：数据/机器/口径）／`[假设]`（取值依据 + **错了会怎样**）／
`[外源]`（出处 + 可靠性）／`[推导]`（所依据公式）之一，**未标记即视为待补**；
**已定参数**（配置默认值、门禁已裁决值）不强行标记，但须**括注依据编号**（如「已定 `L0-S3`」）。
表格可整体声明（如「上表除标注 `[假设]` 的两行外，其余为 `[推导]`」），避免逐格标注破坏可读性。

**为什么这条要写成硬约束**：只检查「有没有标记」时，`[实测]` 会退化成一张免检通行证
——把数字统一打上它就能让检查器放行（实测教训：本 skill 自己产出的方案里，加法推算的
「约 12 条 span」与将来才验收的「问题数 3 个」都标了 `[实测]`，当时六项检查一处没抓到）。

**公式写完必须做「路径枚举交叉核对」**：把系统的所有产出路径列出来
（实测案例：纯文本路径 / 表格路径 / 层级路径），逐条问「这条公式覆盖它了吗」；
未覆盖的要么加权并入公式，要么**显式写「未覆盖声明」**。
实测缺陷：原公式只算文本路径，漏掉表格「每段重复表头」的容量损失，导致块数低估 9%。

**公式里的每个量必须带单位，且同一张表内的量纲口径一致**：实测缺陷——同一张成本表里
「向量存储」写了「4 字节」、「正文存储」省了单位，读者无法复现（中文按字符还是按 UTF-8 字节，差 3 倍）。
**缺单位等于 `[推导]` 不成立**。

**为什么欠账行不许写计数**：与版本号同类——**手写的计数就是第二处可矛盾的值**
（实测交付物两次出现「自述数与实际标注数不符」）。回填清单本身也**不写「共 m 项」**，逐条列出即可。

**状态否定**（第 4 条下的子规则，**不增加硬约束条数**）：写「无 X／没有 X／未实现 X」时，
**同一行要能指出证据**（来源标签 `H1`／四类标记 `[实测]`／本地文件行号）。
**为什么**：`self_check.py` 专设一项查这个，查不到报 ℹ️ 提示项（**不进退出码**——否定句在决策语境里合法，
机器分不清「选择不做」与「断言没有」，而 ⚠️/退出码 2 的信誉必须留给真正未核的项）。
实测教训：本 skill 自己产出的计划文档里写着「无并发保护」，事实上是
「**有**原子替换写、**无**跨进程并发控制」——**否定句是对世界的断言，漏一个限定词就从真话变成假话**，
而既有机械检查全是形式检查、抓不到它。写不出证据时，「**本次未核：…**」是合法出路
——**明示未核优于假装已核**。

**术语两条**：① **自造术语首次出现必须给「一句话定义 + 一个反例」**，否则改用现成词
（实测反例：自造「就低可见」，读者必须反推）；② **禁止用数学符号表达业务语义关系**（⊂／≥／∩），
除非附「人话对照表」（实测：用 `public ⊂ internal` 表达权限偏序，形式感有了、语义漂了
——这种**伪形式化比直接说错更隐蔽**；正确写法是「用户密级 ≥ 文档密级才可见」+ 3×3 可见性对照表）。

### 5.3 契约配断言与反向边界（硬约束 5）

**契约类章节必须配「可执行的验证」**——只写「谁保证」不够，每条契约要求都要有对应的
**入库前断言 + 违约处置**（实测案例：必填字段齐全／`char_start` 单调不减／幂等连跑比对 hash／
未知类型统计，各带「拒收/告警/计数」处置）。无验证手段的契约只是纸面约定。

**「什么情况下不该用这套设计」与「已知限制清单」的区别**：**限制清单讲「我没做什么」，
反向边界讲「什么时候这套方案本身就不划算」**。实测产出：6 条不适用场景 + 判断口径
（本例：「有结构 + 上万量级 + 要增量 + 要溯源」四条同时成立才划算，缺两条以上即改用现成方案）。

**安全边界被新机制绕过**：新增一层中间层（缓存／索引／代理／批处理）时，
原系统靠「每次调用都过一道关卡」实现的安全与一致性会被跳过：实测案例——知识检索按
`allow_<role>` 在**检索期**过滤，加缓存后**命中即不再走检索**，缓存键缺 `role` 就造成跨角色泄漏。
要求写成**可执行断言**并单列进验收项（如「`role=hr` 命中过的答案，`role=employee` 问同一句必须 miss」）
——**它不是实现细节，是这类需求的头号失效模式**。

### 5.4 意图链（硬约束 6）

**「最终设计决策」章每个点都要让读者一眼看出「这个决策要什么」**：
①天花板条目（R 级）按「**要什么 → 备选 → 权衡 → 推荐与理由 → 放弃的代价**」展开，
其中「要什么」是标题（如 `R1 解析范围——「依赖图从哪些文件建」`）、
「放弃的代价」必须显式写（选中 A 意味着放弃了 B 的什么）；
②决策依据（缺口/事实）按「**要什么 → 现状缺口 → 后果 → 对标印证 → 驱动决策**」展开；
③打包默认项（D 级）表格必须含「意图（要什么）」列。
禁止回到「维度｜推荐｜证据｜代价」的单行表格——那会让读者看不到选取意图。

### 5.5 自洽性：为什么必须抽象成通用约束（硬约束 8）

**根因**：**一致性核验的适用范围被逐个写死在具体对象上**（只核「叙事↔字段表」「步骤↔来源」
「路径↔公式」），没抽象成通用约束，于是同一类缺陷换个对象就漏。
实测：一轮 845 行交付物被评审判出 6 处缺陷，其中 4 处（公式口径↔决策章、声明范围↔执行范围、
字段表↔施工步骤、验收入口↔施工路径）根因是同一个。
**声明型内容全文只许出现一次**：层级/档位、范围自述、版本号这类「声明」在文档里**只写一处**，
别处引用不重述——两处各写一遍必然产生漂移（实测缺陷：文档头部写「参考档 ≤600」、§0 写「设计档」，
两处矛盾，被评审判为「首稿不自洽」，8a 因此扣分）。
**核验不通过时按矩阵最后一列处置**——每一对都必须有「怎么办」，
只有「能发现」没有「怎么处理」的核验等于没核。

### 5.6 施工路径的步骤划分（硬约束 9）

**P 步骤必须由本需求的数据流／依赖关系反推**，不是套模板：输入→解析→建模→核心算法→渲染→验收
这类顺序来自需求本身。交付文档的章节骨架（0–9 节，见主文件的文档结构表）是稳定的，**但步骤划分不是**。
不同需求形态允许不同的段落结构（对照 `examples/full-walkthrough.md`：样例 A 为**六节结构**、
只示范 P0 与 P3 两步的完整写法；**完整阶段映射 P0–P8 见本文件 §二**；样例 B 组合型降级只有四段、无 P 步骤）。

**自检**：若两次不同需求的交付长成相同 P 骨架，说明执行时复刻了模板——回查每步是否都能追溯到本需求 L0 裁决或 L2 代码。
**但事后自检不够，必须补前置动作**：开写 L3 之前，先把本需求的数据流链写成一行
（例如「证据→编号→组装→归一→处置→归因→拒答→坐标」），**再按这条链切步骤**，
并在交付文档 §6 显式写出「步骤划分依据 = 该数据流链」。

### 5.7 「提示词必须可复制」为什么写成硬约束

三件套里的「指令模板」如果只是描述性文字，施工方就得自己重写一遍，
而重写的那一遍不受任何约束——**可复制是这条约束唯一能被检验的形态**。


### 5.8 九条硬约束的判据细节（从 `SKILL.md` 归并，主文件已精简为一句判据）

#### 5.8.1 第 2 条：业务实现叙事章的「规格六条」与图

「业务实现叙事」一整章要满足六条：①**每个字段只有一个权威处**（字段表定义，叙事只引用）；②**五段式与三段式的名字必须定义**（说出"输入/处理/输出"各是什么，别只写这三个词）；③**按阶段数分档**（两段就写两段，不要凑成五段）；④**配一个贯穿样例**（同一份样例数据从入口走到出口）；⑤**业务诉求全表**——需求方原话逐条对应到章节位置；⑥**位置固定在 §1**。

反面形态（实测被用户点名）：把流程叙事当业务叙事写；把字段解释散落在叙事与字段表两处；样例换过三次对象，读者对不上。

图的设计：模块数据流图用 `flowchart TD`（上下布局）+ 单行节点文字 + `subgraph` 分阶段（输入／核心／输出／消费方）。**skill 执行流程图不进交付文档**——那是账本职责，混进来会让交付物变成过程报告。

#### 5.8.2 第 4 条：四条细则

1. **标记口径**：**估算类数字**必须属于 `[实测]`／`[假设]`／`[外源]`／`[推导]` 之一，**未标记即视为待补**；**已定参数**须**括注依据编号**。实测被用户在交付物里抓出 `单块 <1ms`（无测量条件、无来源）。
2. **公式写完必须做「路径枚举交叉核对」**：把所有产出路径列出来逐条问「这条公式覆盖它了吗」；未覆盖的要么加权并入，要么**显式写「未覆盖声明」**。实测漏算使块数低估 9%。
3. **公式里的每个量必须带单位，且同一张表内的量纲口径一致**——**缺单位等于 `[推导]` 不成立**。实测：中文按字符还是按 UTF-8 字节差 3 倍。
4. **状态否定也是论断**：写「无 X／没有 X／未实现 X」时，**同一行要能指出证据**（来源标签 `H1`／四类标记 `[实测]`／本地 `文件:行`）。查不到报 ℹ️ 提示项、**不进退出码**。写不出证据时「**本次未核：…**」是合法出路——**明示未核优于假装已核**。

**术语两条**：① **自造术语首次出现必须给「一句话定义 + 一个反例」**，否则改用现成词；② **禁止用数学符号表达业务语义关系**（⊂／≥／∩），除非附「人话对照表」。

#### 5.8.3 第 5 条：为什么「安全边界被绕过」是头号失效模式

新增一层中间层（缓存／索引／代理／批处理）时，原系统靠「每次调用都过一道关卡」实现的安全与一致性会被跳过。实测案例：权限过滤施加在检索函数内部，而加在检索之上的缓存键不含 `role`，于是 HR 命中过的答案会漏给员工——**越权泄漏，比需求方自己说的「近似问题串答案」严重一个量级**。要求写成可执行断言并单列进验收项，不能只写「注意权限」。

**反向边界与限制清单的区别**：限制清单讲「我没做什么」；反向边界讲「什么时候这套方案本身就不划算」（如数据量低于阈值时引入索引只会更慢）。后者是资深设计的标志之一。

#### 5.8.4 第 6 条：意图链的三种展开

- R 级（天花板条目）：「**要什么 → 备选 → 权衡 → 推荐与理由 → 放弃的代价**」，「放弃的代价」必须显式写；
- 决策依据：「**要什么 → 现状缺口 → 后果 → 对标印证 → 驱动决策**」；
- D 级（打包默认项）：表格必须含「意图（要什么）」列。

禁止回到「维度｜推荐｜证据｜代价」的单行表——那会让读者看不到选取意图。

#### 5.8.5 第 8 条的根因

**一致性核验的适用范围被逐个写死在具体对象上**（只核「叙事↔字段表」「步骤↔来源」「路径↔公式」），没抽象成通用约束，于是同一类缺陷换个对象就漏。矩阵表体、三种收尾状态、两条例外规则见 `delivery-checklist.md` §一。

#### 5.8.6 第 9 条：步骤划分为什么必须从数据流反推

章节骨架（0–9 节）是稳定的，**但分步实现路径的步骤划分必须由本需求的数据流／依赖关系反推**。复用上一需求的步骤骨架会让读者看到一条与本需求无关的实现顺序。**事后自检不够，必须补前置动作**：开写 L3 之前先把本需求的数据流链写成一行，再按这条链切步骤，并在 §6 显式写出「步骤划分依据 = 该数据流链」。


## 六、L3 各条的实测来历（从 `SKILL.md` 的叙事里归并过来）

> 判据在 `SKILL.md`，本节只放「这条是怎么被撞出来的」。
> 保留它的理由：删掉来历之后，规则会显得像拍脑袋的偏好，下一个人会理直气壮地把它删掉。

### 6.1 文档结构为什么是「唯一来源」

v1.18.3 审计发现同一份 SKILL.md 里**并存过三套编号**：本表旧的 0–7 版 / 分节核验的 §0–§8 /
正文里的「第 4 节」（两种含义）。根因是同一份「文档结构」被写了多处、改一处忘一处。
**所以本表是唯一来源，别处只准指回编号。**

### 6.2 两处「不独立成章」的理由

同一份信息写两遍，是交付物变长的主因之一；删掉重复不损失任何信息。
- **对标带来的改动**并入第 2 节「决策依据」表——两者同为「缺口 → 决策」的映射，分两处写必然重复；
- **读码坑清单（`K<n>`）不单列成表**：坑在正文原位用 `K<n>` 引用，「它怎么做 + 与我的方案差在哪 + 代码位置」
  写在第 5 节的读码要点里，附录只留一张**纯编号索引**（一行一条，不重述内容）。

### 6.3 落盘时序是怎么来的（v1.56.18）

三个独立 agent 各跑 20+ 分钟、合计留下 **48 份真实取证文件**（上游源码 + 针对本项目的探针脚本），
而**产出物目录自始至终为空**（[实测] 账本 v1.56.18）。它们走的顺序都是 L0 → L1 → L2 → L3 → 最后写文档，
全都死在取证阶段——那些工作换算不成任何可评分的成果。
**失败时唯一能保住的就是已经写进文件的部分**，所以「先落盘」是硬规矩，不是习惯。

v1.56.25 澄清（盲跑 7 撞出来）：**先落盘的是骨架，不是完整的 §0**。门禁 1 的痛点/约束表要等门禁 1 走过
（问需求方，或按降级路径从材料与本地代码推断）才回填，L1.0 的探活那时也还没做。
把「第一个动作是先落盘」误读成「先把 §0 写完再动」会卡住——落盘规矩**不改变执行顺序**，
只要求「已经知道的，当场写进文件」。

### 6.4 为什么要给体量立「代理指标」的教训（v1.18.0）

曾自定「参考档 ≤600 行／设计档 ≤900 行」，那是**无测量、无外部依据的拍脑袋整数**；
三份历史交付 845／927／773 行的中位数是 845——**阈值比历史中位数还低**。后果两条：
①被独立评审当成评分依据，把质性判断「过重」锚定成机械判断「超行数」；
②我以「改声明为设计档」绕过了它，一分没减。

**凡立代理指标，先问三句：它想代理什么？有没有直接判据？会不会被绕过或锚定评审？**

### 6.5 第 0 节的层级+档位声明

它是给评审人看的一句话：「本文档是**模块级／系统级**的**参考／设计／规范**文档」。
不写会被用错尺子量——实测中用户**连续四次**纠正我拿更高层级（架构级）或更重档位（流程规范）去评估材料。
**声明在前，能避免整场评估跑偏。**

### 6.6 分节核验里 §3 那一条的遗留说明

旧条要求把欠账行的 N/x/y/m 逐项数一遍，**与硬约束 4「不得写计数」互相抵消**：
欠账行里根本没有这些数，该条永远无对象。**已废**——现在只要求「欠账行存在、且不含任何计数」。
没有计数，「自述数与实际标注数不符」这种矛盾就无从发生。

## 九、落盘时序的来历与四条动作

>
> ①读需求后的**第一个动作**是把交付物文件建起来，写下**此刻就能写的一切**——层级+档位声明、
> 已确定的 `[假设]`，并自带一行「本次进行到 §0」。
> ⚠️ **先落盘的是骨架，不是完整的 §0**（v1.56.25 澄清，盲跑 7 实测撞出来的）：痛点/约束表要等门禁 1 走过才回填，探活那时也还没做。把「第一个动作是先落盘」
> 误读成「先把 §0 写完再动」会卡住——落盘规矩**不改变执行顺序**，只要求「已经知道的，当场写进文件」。
> ②此后**每写完一节立刻写盘**，在当次工具调用里追加，当次即写；
> ③取证阶段拿到的外部代码位置与探针结论，**当场**抄进对应章节，别攒着统一整理；
> ④中途若被迫中止，文件要自带一行「本次进行到 §N，以下为已完成部分」——
> 半份能读的交付物远远好过零份。

## 十二、九条硬约束的正文细则（主文件只留标题与首句）


**1. 必须从一句模糊需求出发**

即使实际走富信息路径（需求自带设计），开头也要展示原始模糊需求原话 + 它缺哪些决策 + 为何转向验证。读者必须看到起点是模糊的，否则丢失 skill 的核心卖点；

**2. 两章前置**

「业务实现叙事」必须是**整块一章**而不是小结；**模块全景先行**：一句话定义 + 数据流图 + 做什么/不做什么边界表 + P 步骤如何拼装成模块。规格六条、图的画法（`flowchart TD`／`subgraph` 分阶段／**skill 执行流程图不进交付文档**）见 `references/l3-mode-map.md` §5.1；

**3. 交付文档与服务者账本分离**

过程记录（各步骤实际动作、读码纠错、评分）一律归 `references/verification-log.md`，**不进交付文档**；交付文档只放结论／决策／路径；

**5. 论断必须可核查**

每条契约要求都要有对应的**入库前断言 + 违约处置**（无验证手段的契约只是纸面约定）；必须写「什么情况下不该用这套设计」——限制清单讲「我没做什么」，反向边界讲「什么时候这套方案本身就不划算」；新增一层中间层（缓存／索引／代理／批处理）时**必须回答原有的安全边界会不会被绕过**，写成可执行断言并单列进验收项（**它不是实现细节，是这类需求的头号失效模式**）。实测案例见 §5.3；

**6. 决策必须带意图链**

①R 级按「**要什么 → 备选 → 权衡 → 推荐与理由 → 放弃的代价**」展开，其中「放弃的代价」必须显式写；②决策依据按「**要什么 → 现状缺口 → 后果 → 对标印证 → 驱动决策**」；③D 级表格必须含「意图（要什么）」列。禁止回到「维度｜推荐｜证据｜代价」的单行表。细则见 §5.4；

**7. 对标必须附链接**

每个参考仓库给 GitHub 链接，逐仓库写「为什么参考（值得借鉴的设计）＋为什么不全抄（它的实现为何不可用）」。**参考的是设计决策，不是实现**；

**8. 交付文档必须自洽**

根因：**一致性核验的适用范围被逐个写死在具体对象上**，没抽象成通用约束，于是同一类缺陷换个对象就漏。硬规则：交付前按 `references/delivery-checklist.md` §一 的矩阵**逐对核验、逐对打勾**；**矩阵每一对都必须落到机械动作上**——写不出机械动作的对，说明核验还没设计完；核验不通过按表里「怎么办」列处置，**只有「能发现」没有「怎么处理」的核验等于没核**。**声明型内容全文只许出现一次**（层级/档位、范围自述、版本号只写一处，别处引用不重述）。触发条件：交付文档一旦出现交叉引用（公式↔决策、字段↔步骤、验收↔入口、契约↔断言、叙事↔字段表、路径↔覆盖…）就必须逐对核验。根因与反例见 §5.5；

**9. 施工路径的写法**

每个施工步骤给完整可复制的 prompt（Spec／TDD 各按其模式），含「明确不要做什么」；**P 步骤必须由本需求的数据流／依赖关系反推，禁止复用上一需求的步骤骨架**：开写 L3 之前先把本需求的数据流链写成一行，**再按这条链切步骤**，并在 §6 显式写出「步骤划分依据 = 该数据流链」。自检方法、样例与阶段映射见 §5.6；

## 十三、通过信号的三条附加要求

原文（原先内联在 `SKILL.md` 的「通过信号」那一格）：

①**可判**（非谓词措辞会被 `self_check.py` 第 8 项判违规）；②**在目标项目现有的测试栈里跑得起来**——若这一步的断言需要新建测试台（例：要断言前端回调次数，而 `package.json` 里除 `dev`／`build`／`lint`／`preview` 外没有任何前端测试框架），**必须在同一步写明"需要新建什么、代价多大"**，只写断言形式等于把成本藏起来（施工方回访实测：两条通过信号在目标项目里没有可执行形态，施工方自建两套验证台才拿到证据）；③**依赖非确定性输出的信号必须带容差**——LLM 路由、语义判断这类断言的结论会抖动，必须写明"允许偶发几次／观测几次判定／判据是事实还是概率"；把"全部通过"当硬信号，会得到一个测不准的红（施工方回访实测：某场景四次观测 FAIL 2／PASS 2，与改动无关） |

## 十四、交付文档的 0–9 节结构、两处不独立成章、层级与档位

### 交付文档的 0–9 节结构（唯一来源是本表）

```
0. 定位与档位声明（引需求方原话 + 缺哪些决策 + **声明本文档的层级与档位**；需求方不可达时**首行是不可达声明**、层级与档位紧随其后——两条都要，顺序固定，别二选一）
1. 业务实现叙事（整块，面向业务读者；规格见硬约束 2）
2. 最终设计决策表（门禁 4 收敛产物 + 同表的「决策依据」列：对标发现的缺口 → 决策）
3. 量级与估算（公式 + 覆盖声明 + 单位；章首「实测欠账行」；见硬约束 4）
4. 契约与边界（每条契约配入库前断言 + 违约处置；见硬约束 5）
5. 对标结论（附仓库链接 + 逐仓库"为什么参考/为什么不全抄"取舍；读码要点写在此节；**凡发生降级，本节首行明示走到哪一级**（①部分匹配／②跨语言跨栈／③退回 spec-development／④无先例）；需求方不可达、需求过泛只能当设计范本，都算降级，不只 0 候选链。级别 ①–④ 的定义见 `l1-search-recipes.md` §十一，此处只写编号。候选充足、确实没降级时，写一句「未走降级链」也算明示）
6. 模块全景（一句话定义 + 数据流图 + 边界表 + 步骤拼装关系 + 步骤划分依据）
7. 分步实现路径（主体，每步：目标→执行流程→提示词模板→通过/翻车信号→验收证据→来源；**每步必须点名改哪个文件、哪个符号**——实测不到单一入口时，写清有几个触点、各在哪。「在唯一入口处做映射」这种写法会让施工方停住：施工方回访实测，代码里实际有 5 个触点，交付物一处都没点名）
8. 验收清单（每条带可观察证据）
9. 已知限制与未解项（含"什么情况下不该用这套设计"的反向边界；§9.1 为实测回填清单；**未解项与「下一步」分开列**——未解项是"本次没核实的"，下一步是"给需求方与施工方的下一个动作"）
```

### 两处「不独立成章」与第 0 节的层级+档位声明

> **两处"不独立成章"**：
>
> - **对标带来的改动**：并入第 2 节「决策依据」表——两者同为"缺口 → 决策"的映射，分两处写必然重复；
> - **读码坑清单（`K<n>`）**：**不单列成表**。坑在正文原位用来源标签 `K<n>` 引用即可，附录只留一张**纯编号索引**（一行一条，不重述内容）；理由见 `l3-mode-map.md` §6.2。

> **第 0 节的层级+档位声明是给评审人看的**：一句话写清「本文档是**模块级／系统级**的**参考／设计／规范**文档」。不写会被用错尺子量——实测中用户连续四次纠正我拿更高层级或更重档位去评估材料（见 §6.5）。
