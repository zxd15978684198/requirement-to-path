# 交付文档自检：⑭ 引用关系矩阵 + 交付前清单

<!-- self_check: genre=reference -->

> 本文件是 SKILL.md **L3 硬约束 8** 的表体与 **「执行后自检清单」** 的唯一权威处。
> 从 SKILL.md 移出，原因：这两块只在**交付前**用一次，却让每次加载 SKILL.md 都付全额 token。
> SKILL.md 里留下的是**路由与触发条件**（什么时候必须核、举证门槛是什么），表体与逐项勾选动作在这里。
>
> 用法：交付文档写完 → 先跑 `python references/self_check.py <交付文档.md>` 拿机械结论（附退出码），
> 再按本文件 §二 逐项打勾，§一 的矩阵逐对核验。

## 一、⑭ 引用关系矩阵（硬约束 8 的表体）

| A ↔ B | 核验什么 | 机械动作 | 核验不通过怎么办 |
| --- | --- | --- | --- |
| 量级公式 ↔ 决策章的预算/口径定义 | 公式里每个变量的定义与取值，与 R/D 条目写的是同一口径 | 把公式变量逐个抄出来，回决策章找定义比对写法 | 改公式去对齐决策；若决策本身漏了这个参数，回决策章补一条 D 级决策——**不许**让公式另立一套口径 |
| 数字标记的自述范围 ↔ 实际标注范围 | 声明的覆盖范围不得超出实际标注的范围（写"全文"就得全文都有）；**声明型内容全文只许出现一次** | **扫全文**：①正则扫裸数字 ②扫"全文／所有／每个"范围词 ③逐个声明型短语（**层级/档位**、范围自述、版本号）统计全文出现次数，**>1 处即核对是否逐字一致**（实测漏点：文档头部的定位行与 §0 的档位声明分处两地） | 二选一：把口径收窄到实际范围，或按范围补标；两处声明冲突时**以 §0 为准并改掉别处**——**两者都不做不许交付** |
| 字段表 ↔ 施工步骤 | 每个必填字段在某个 P 步骤里有明确的写入动作；反向：P 步骤写出的字段都在字段表里 | 双向列一遍取差集 | 差集非空即回补：字段缺落点 → 在对应步骤补写入动作；步骤写了表外字段 → 补进字段表或删掉该字段 |
| 验收项 ↔ 施工路径定义的入口 | 验收项引用的命令／函数／文件必须在施工路径里定义过 | 抽出验收项里所有标识符（命令名／函数名／文件名），回施工路径逐个查 | 在施工路径补定义，或删掉该验收项——**不许**只改措辞让它"看起来定义了" |
| 契约条款 ↔ 入库前断言 | 每条契约要求都配可执行断言 + 违约处置，不只是"谁保证" | 逐条对，缺断言即不合格 | 给不出断言的条款标 `[待定]` 并列进未解项，写明现在给不出的原因 |
| 业务诉求全表 ↔ 阶段/字段/决策编号 | 全表引用的每个编号都真实存在 | 编号回查落地 | 编号查不到 → 修编号；若该诉求本就没有对应决策 → 补一条决策，或删掉该诉求行 |
| 产出路径 ↔ 公式覆盖 | 每条产出路径都被公式覆盖，或显式声明未覆盖 | 路径枚举交叉核对 | 未覆盖路径 → 加权并入公式，或写进覆盖声明的「未覆盖」清单（**必须显式**，不许沉默放过） |
| 叙事引用的字段 ↔ 字段表 | **字段名集合以 §1 业务叙事为唯一决定方**，§2 字段补表逐一对齐；两向差集都须为空 | **双向列一遍取差集**；§2 字段补表 不得出现 §1 未定义的字段，§1 定义的字段也不得漏进 §2 字段补表 | 差集非空即回补：§1 有而 §2 字段补表 缺 → 补进 §2 字段补表 的类型与必填；§2 字段补表 有而 §1 无 → 删掉该字段，或回 §1 补定义（**不许两处各定义一次**） |
| 施工步骤来源列 ↔ 封闭域 | 来源落在 `L0-P<n>`／`L0-C<n>`／`L0-D<n>`／`L0-S<n>`／`R<n>`／`D<n>`／`C<n>`／`H<n>`／`K<n>`／`账本vX.Y[.Z]`／`repo/path:L<行>`／`repo/path:L<a>-L<b>`／`repo/path#符号名` 内（**L0 四类都要列**：门禁 1 产 `L0-P`／`L0-C`、门禁 2 产 `L0-D`、门禁 3 产 `L0-S`；旧文只列 P/S），填不出就删步骤。**本行枚举必须与 `self_check.py` 的 `ALLOWED_SOURCE_PATTERNS` 逐项同集**——同一个封闭域写两处而集合不同时，以本表为准会把合法的 `L0-C1`／`L0-D2` 判成越界，再按本表处置**删掉一个合规步骤**。**四条写法明文**：①**来源格只放标签**——整格写反引号包裹的标签，不夹带说明文字（夹带时脚本报「标签外夹带文字」；若无反引号则按分隔符切成假标签逐条报越界，v1.27.0 实测一次 30+ 条）②标签一律**反引号包裹**③仓库路径**必须带字面 `repo/` 前缀**（写成 `repo/owner/name:path#符号名`）——少这个前缀会被判越界 ④**核验范围只有施工步骤表**——表头含「步骤」，**或**含「指令模板／通过信号／翻车信号／提示词」之一（与 `self_check.py` 的 `STEP_HEADER_CORE`／`STEP_HEADER_SIGNAL` 逐项同集）的表才逐行核；**「阶段」不算**——阶段映射表、阶段汇总表都用它，把它算进来会把「阶段／模式／理由」这类映射表当成施工步骤表并误报"缺来源列"（实跑翻过车）；门禁 4 裁决表、说明表写自然语言出处属正常，不判越界；反过来**施工步骤表缺「来源」列会被报违规** | 逐个查；用 `#符号名` 形式时附录须说明未给行号的理由；**跑 `self_check.py` 并附输出**（来源列写在施工步骤表的单元格里也照样核——脚本会找表头名为「来源」的那一列） | 填不出来源 → **删掉该步骤**；不许补一个勉强出处 |
| 逐仓库取舍 ↔ 失效条件（**一票否决格**，P0-1） | 每个参考仓库都写了"**如果我抄它，会在什么条件下坏**" | 逐仓库对：该仓库的机制在**本需求场景**下的失效条件是否写明；写不出即视为"只抄了形" | 补写失效条件；若它在自家场景**必然坏掉**，降级为"设计参考"或直接排除——**不许留在"要抄"清单里** |

**三种收尾状态（与交付前自检清单第 8 条逐字同规则）**：矩阵每一对只许以 ①**已核**（打勾）②**`N/A：<原因>`**（该行依赖的输入本次不存在，原因必须具体——典型是 0 候选导致 §5 为空）③**未完成** 三者之一收尾；**非 0 候选场景写 `N/A` 判漏核**。矩阵本体必须自带这第三态：只写在清单里的状态等于没定义。

**核查自身的两条例外规则**：①**误报白名单**——机械动作会命中"测试输入样例""枚举取值""取值示例"这类合法内容，逐条定性确认后记入白名单并写明理由，否则下一轮核验会被同样的噪音淹没、真缺陷反而被埋掉；②**核查脚本本身要受检**——本次实测中核查脚本把编号拼错了字符（`R1` → `RR1`），一次报出 5 条假失败；脚本报错时先怀疑脚本，再怀疑文档。

## 二、执行后自检清单（交付前硬核对）

任何一项不过，**不得交付**——本清单把散在各层的核对点集中成一张表，交付前逐项打勾（对应门禁通则第 5 条 `🔴 CHECKPOINT` 的语义）：

**开工前（执行序列第 1 步）**
- [ ] **先看现状**：这件能力在被改造的项目里**是不是已经有了**（grep 表／字段／函数／配置／迁移记录／既有测试）？已经有就**把交付物改成回答「现有实现与需求的差距在哪」**，而不是从零规划——实测代价：一个盲跑样本为一件**早已实现**的能力产出了整份实现计划（来历见 `references/verification-log.md` 的 v1.58.0 行）

**L0**
- [ ] 痛点清单每条都被用户逐条确认（降级流程下则每条有 `[推断]`/`[假设]` 标注）？
- [ ] 门 3 的「明确不做什么」非空？
- [ ] 需求方不可达时，`[假设]` 清单已置于交付物**首页**？
- [ ] **每道门禁题都带叙事前提**（先场景后选项，不是裸选项列表）？连续两轮被回"看不懂／缺前提"时，是否已切换到**样例先行**（跑真实样例给用户看实物，再问要/不要/改哪里）？
- [ ] 天花板条目里用户选了与已知失效模式冲突的选项时，是否做了**失败时序推演 + 等价替代 + 重新确认**三步（而非静默采纳）？

**L1**
- [ ] 本次将用到的每个连接器工具都**各探活了一次**（不是只测一个）？
- [ ] `search_repositories` 都带了 `minimal_output: false`？`search_issues` 都带了 `owner`+`repo` 限定？
- [ ] 疑似「已支持」的声称做了**双核验**（`pull_request_read` 看 `merged` + 反向对照搜索）？
- [ ] 需求含模型型组件时，走了 HuggingFace 第二搜索面？
- [ ] 搜索轮次不超过上限（数值见「已知限制」第 2 条；满了是摆给用户裁决，不是自行死磕）？

**门禁 4**
- [ ] 优缺点三分类完整（每条候选都有 ✅/⚠️/❌ 归属）？
- [ ] 影响复杂度天花板的条目逐条征询了？打包默认项**显式列出**（无静默略过）？

**L3**
- [ ] 每步三件套齐（指令模板／通过信号／翻车信号）+ 开发模式标注？**通过信号三问**：①可判吗（非谓词措辞会被脚本判违规）？②**在目标项目现有的测试栈里跑得起来吗**——跑不起来就必须在同一步写明"需要新建什么、代价多大"，不许只写断言形式把成本藏起来？③**依赖 LLM 路由／语义判断这类非确定性输出的信号，写了容差吗**（允许偶发几次／观测几次判定／判据是事实还是概率）？——②③ 两条来历见账本 v1.58.0：施工方回访实测，两条通过信号在目标项目里没有可执行形态（`package.json` 里除 `dev`／`build`／`lint`／`preview` 外无任何前端测试框架），而另一个场景四次观测 FAIL 2／PASS 2 与改动无关
- [ ] 每步**带来源列，且取值落在封闭域内**（`R<n>`／`D<n>`／`C<n>`／`H<n>`／`K<n>`／`账本vX.Y[.Z]`／`repo/path:L<行>`／`repo/path:L<a>-L<b>`（**行区间，v1.53.0 起合法**：读一段实现的标准写法，比单行更可核——单行只证明"那一行存在"，区间证明"这段代码在"；两端要能对上 `a ≤ b` 且 `b ≤` 文件行数）／`repo/path#符号名`；`L0-P<n>`／`L0-S<n>`／`L0-C<n>`／`L0-D<n>` **仅当有 L0 编号产出物**——**四类都要列**：门禁 1 产出 `L0-P<n>`（痛点）与 `L0-C<n>`（约束）、门禁 2 产出 `L0-D<n>`（决策）、门禁 3 产出 `L0-S<n>`（规格）；旧文只列 P/S，**人核的域比机器白名单少两类**）？**这一列必须与 `self_check.py` 的 `ALLOWED_SOURCE_PATTERNS` 逐项同集**——人核的域和机器核的域不是同一个域时，漏核也能勾"全绿"
    - **证据（必须附输出）**：`python references/self_check.py <交付文档.md>`，贴结果**与退出码**（0 = 放行；1 = 有违规；**2 = 0 violations 但有未核项，不放行**；64 = 用法错误）——**没有脚本输出 = 视为未核**。退出码要**当场捕获**、不许凭"看着像通过了"填：`bash: python … ; echo "EXIT=$?"` ／ `pwsh: python … ; $LASTEXITCODE`。交付文档里记成固定一行：`自检：python references/self_check.py <文档> → EXIT=<n>（末行：<原样抄一句>）`——**只写"已自检"不算证据**
    - **脚本不可执行时（无 shell／无解释器）不许默认放行**：改用**人工等价核验**——对照本文的封闭域枚举表核来源列、对照四类标记核 §3 数字、对照固定格式核欠账行、对照 ⑭ 矩阵逐对核交叉引用，并在本清单该行写明「**人工核验，未经脚本**」+ 逐项结论；**该状态一律按"未核"记账（不放行）**，直到在有解释器的环境补跑脚本。理由：脚本不可用是环境问题，**不是判据消失**——把"跑不了"当成"通过了"，正是本 skill 反复治理的那种失明
    - **填不出来源的步骤是"删掉"而不是"补一个勉强出处"？** 用 `#符号名` 形式时，文档附录须说明未给行号的理由？
- [ ] 验收清单每条带**可观察证据**——**最低标准：证据须第三方可复现**（给出命令／文件路径／输出片段任一种）？「我看到了」「看起来对」不算？
- [ ] 每处 `[实测]`／`[外源]` 的**本地**证据真的核过（打开过那个文件、行号对得上），而不只是"路径长得对"？外部证据（`repo/…`／URL）**机核不了**，至少写了一处「本次未核：外部链接无法机核」——**"写了出处"与"出处是真的"是两件事**，第 7 项只查前者
- [ ] **证据路径是相对本文档、还是相对目标项目？** 交付物写在输出目录、被引用的代码在另一个盘的项目里是常态：那种情况下要在**文件前 4000 字符内**声明一次证据根 `<!-- self_check: evidence_root=E:\projects\某项目 -->`（声明后脚本只按声明的根解析、不再看 CWD；不声明时同一份文档**换个目录跑就全报"核不到"**，判据不该随环境漂移）。**可以声明多个证据根（一行一个）**——分析阶段引原项目、施工阶段在工作副本里时，**必须把副本一并声明**，否则施工中新写的探针脚本与验证台会全部报"核不到"，而它们正是回填实测数字的证据（v1.58.0 补：施工方回访实测到"交付物规定的产出与它自己的验收工具互斥"）。**提示**：`.env` 已在可核扩展名内，但配置项优先引提交进仓库的 `.env.example`（v1.56.23 补，来历见 `references/verification-log.md`）

- [ ] 对标附了仓库链接 + 逐仓库「为什么不全抄」取舍，且**取舍引用了 L2 的具体代码位置**（不是"因为它太复杂"这类泛评）？
- [ ] 模块全景（定义 + 数据流图 + 边界）在实现路径之前？
- [ ] 第 2 节「决策依据」表列出了本次对标带来的具体改动（不做流程会怎么做 → 实际怎么做，且**能数出条数**）？
- [ ] 过程记录（实际动作 / 纠错 / 评分 / **旧版本对照**）已移出交付文档？用正则扫 `旧版|上一版|本次修正|本次修复` 与 `v数字→v数字` 这类迭代痕迹词，命中即移出？

## 三、`self_check.py` 的射程与口径（从 `SKILL.md` 资源清单行移入）

> 为什么在这里：资源清单那格只需要说「跑什么、什么时候跑、输出贴哪」。
> 射程边界、各项判据、脚本自身的病史属于**查的时候才看**的内容，
> 而本文件已经是「交付前必读」——放这里不需要多读一次全文。

### 3.1 十三项机械自检各查什么

以下逐项列出，**名称以 `self_check.py` 的 `_CAVEAT` 为唯一权威**（那里是脚本自述，
两边对不上时 `--skill` 模式会 exit 1）：

- **来源封闭域** — 来源格的值必须落在白名单内。
- **声明取值唯一** — 同一族声明只许有一种取值。
- **声明冲突** — 层级与档位两族不许互相矛盾。
- **欠账行计数** — 声称「附输出」就必须真有输出。
- **估算章节数字标记** — §3 里的估算数字必须带四类标记。
- **候选发现记录** — 表头须含「命中数」与「取回条数」。
- **标记与证据配套** — `[实测]`／`[外源]` 必须同行指得出
  `文件:行`／`repo/...`／`账本 vX.Y`／`H<n>`／URL；**本地文件还须真能解析到**
  ——相对目标项目而非相对本文档的路径，先在文件头声明 `evidence_root`
  （见 `SKILL.md`「两处容易读错的地方」②）。
- **L3 通过信号可判** — 有「通过信号」列的步骤表里，下列四种写法判违规：
  ①非谓词措辞（如「数量级」「明显改善」）②「取消注释…」式空指令
  ③「先删后写」与「失败后旧块仍在」并存 ④`where={"K"}` 的 K 全文未定义。
- **引用完整性** — 来源列／依据列引用的 `R<n>`／`D<n>`／`C<n>`／`H<n>`／`K<n>`
  必须有定义处，悬空即违规。
- **章节骨架** — §0–§9 缺节、或标题下正文被清空 → 违规。
- **账本版本引用** — `账本vX.Y` 必须在账本里存在。
- **自检留痕** — 文档声称贴了 `self_check.py` 输出、或留着「待回填」占位符，
  而全文没有 `EXIT=<n>`／`退出码：<n>` → 违规：**公告 ≠ 证据**。
  只在出现占位符或「原样粘贴」类声明时才生效，**不要求每份文档都带退出码**。
- **承诺落地** — 分析章里「必须大于／应设为／建议…」这类**建议取值**，
  若那个数字**全文只出现这一次** → 违规：
  **写进文档的承诺与写进文档的步骤是两份东西**，施工方无从知道该在哪一步改它。
  判据不问「作者有没有承诺」（那是措辞），只问「这个只出现一次的取值有没有落点」（那是事实）。
  来历见账本 v1.58.0：一份交付物给出了保留硬上限的目标值而全文没有任何一步去改它，
  施工方照着做完，那条最坏路径**形同虚设**。

**提示项（唯一一项）**：**状态否定的证据**。它是唯一核「说的对不对」而不是「引用得对不对」
的一项——把「无 X／没有 X／未实现 X」当论断查、要求同行能指出证据，
判为 ⚠️ 未核而**非**违规（机器分不清「选择不做」与「断言没有」）。提示项不进退出码。

### 3.2 三条射程边界（不知道就会误判成"脚本漏核了"）

**① 后四项只对 L3 交付物生效。**
章节骨架／引用完整性／**承诺落地**三项只对 L3 交付物启用：
**标题行**里出现 ≥3 个 L3 章节名才启用，否则整项不适用——
**正文里列举章节名不算**，否则参考文档会被误判成交付物。
引用完整性先剔 ``` 围栏，但**未闭合的围栏**会让配对错位、围栏之后可能整段不查
——交付前扫一眼围栏是否成对。拿它们去跑普通 Markdown 会把 `R3` 这类普通代号判成悬空、
把没有 §0–§9 的文档判成缺节（实测误报，已加守卫）。

**② 「声明取值唯一」只有一半在机器射程内。**
脚本通用模式只查「同一族出现**多种取值**」，
**「同一个值写在两处」这种重述查不出**——那要靠 ⑭ 第 2 对人工扫全文，
或由维护者跑 `--skill` 模式。**别把脚本的"声明唯一"当成"重述已核"**。

**③ 第 7 项另有一层「可核性」。**
`[实测]`／`[外源]` 引用的**本地**证据（`文件:行`／`账本 vX.Y`）必须真的能核——
文件按「文档目录 → 祖先目录 → CWD」解析得到、行号不越界、账本版本存在，
否则报 **⚠️ 未核**（不是违规）。`repo/…`／URL 这类外部证据**天然不可机核、本脚本不判**，
所以「未核项为 0」**不等于「证据全真」**。

### 3.3 退出码四态

- `0` = 放行
- `1` = 有违规
- `2` = 0 violations 但有 ⚠️ 未核项（**未核 ≠ 通过**）
- `64` = 用法错误：没给路径／路径不存在／传进来的是目录／文件不是 UTF-8／
  一次给了多个路径——这几种旧实现全是裸 `open()` 抛栈回溯 + 退出码 1，
  会被读成"文档有违规"，v1.48.0 已统一挡成 64。

另有 `ℹ️ 提示项`，不影响退出码。

### 3.4 脚本自身的病史（决定"报错时先怀疑谁"）

**脚本报错先怀疑脚本**——它有误报史也有漏报史
（来源检查曾对表格行整体跳过、数字检查曾恒返回空，两处已修）。
白名单或判据改动后，必须用**正反例各一个**跑过再采信——
**反例要打"曾经静默通过的路子"**（历史上最严重的四个漏洞全是"报不出"、不是"报错"）。

## 四、交付前的机械举证与两个容易读错的绿灯

> 清单表体见 **`references/delivery-checklist.md` §二**（L0／L1／门禁 4／L3／全程 五组勾选项 + 每项的举证要求）。
> 交付前逐项打勾，**任何一项不过不得交付**；机械部分的最低举证是
> `python references/self_check.py <交付文档.md>` **并贴出输出与退出码**（0 放行／1 违规／2 未核不放行／64 用法错误）——**没有脚本输出现场 = 视为未核**。
> 但**退出码 0 只等于"机械项没查出问题"，不等于清单打勾完毕**——它只是机械部分的最低举证，
> 勾选项里的人工部分（语义相关性、证据是否真支持结论）脚本核不了；脚本自印的口径行就是这句。
> 两处容易读错的地方，写在这里而不是让脚本去猜：①**`--skill` 的绿灯不是能力证明**——它只证明 SKILL.md 自身一致（版本对账／哨兵位置／禁用形态／自述项数与实现一致），
> "这个 skill 跑真实需求有效吗"只能由「真实需求 → 交付物 → 施工方回访」证明；②**`[实测]`／`[外源]` 引用的本地证据必须真的能核**
> （路径按「文档目录 → 祖先目录 → CWD」解析得到，且行号不越界），核不到报 ⚠️ 未核而不是违规——**"写了出处"与"出处是真的"是两件事**。
> **若证据路径本来就相对「目标项目」而不是相对本文档**（交付物写在输出目录、被引用的代码在另一个盘的项目里，这是常态），
> 就在**文件前 4000 字符内**声明一次证据根：`<!-- self_check: evidence_root=E:\projects\某项目 -->`。
> 声明之后脚本**只按声明的根解析、不再看 CWD**；声明的根不存在时该声明被忽略（写一个根不能免检）。
> **可以声明多个证据根（一行一个）**——典型场景是「分析阶段引原项目、施工阶段在工作副本里」：
> 只声明原项目时，施工中新写的探针脚本与验证台会**全部报"核不到"**，而它们恰恰是回填实测数字的证据。
> 施工发生在副本，就把副本一并声明（v1.58.0 补，来历见账本：施工方回访实测，交付物规定的产出
> 与它自己的验收工具互斥——`P9` 要求回填实测数字，而证据根指向只读原项目）。
> 为什么要声明：不声明时同一份文档**从项目目录里跑是零告警、换个目录跑就全报"核不到"**——
> 结论取决于你站在哪里运行脚本，而**判据不该随环境漂移**。未声明时告警会列出**它试过哪些根**，照那一行补声明。
