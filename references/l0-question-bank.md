## 一、通用三类问题框架

无论什么需求，A/B/C 三组都要覆盖：

| 组 | 目的 | 挖什么 |
| --- | --- | --- |
| **A 现状与痛点** | 挖隐性知识 | 他现在实际怎么做、最烦哪一步、怎么绕过去的 |
| **B 环境与约束** | 决定方案空间 | **技术栈**、目标存储、量级、频率、触发方式、交付严格度 |
| **C 边界与失败** | 划定安全线 | 删除/异常/失败怎么办、明确不要什么 |

**提问顺序**：先 A（建立信任，从痛点切入）→ 再 B（具体但客观）→ 最后 C（涉及取舍，需要前两组铺垫）。

**B 组必须问技术栈**——它决定候选项目的可选项。漏问这一条会导致搜到的候选全部无法使用（实测：漏问技术栈后第一轮搜出的 5 个语义缓存项目全是 JS/Go/Ruby，没有一个是目标语言）。

## 二、数据同步 / 索引类（完整题库，13 题）

### A 组 · 现状与痛点

**1. 目前数据是怎么进目标存储的？由谁触发？**
- 手工跑脚本 / 定时任务自动跑 / 服务里自动触发 / 还没有，正要建

**2. 现在的同步靠什么决定"要不要重新处理"？**
- 每次全量重建 / 按修改时间筛 / 有哈希判断 / 没判断，重复写

**3. 现在的痛点具体是哪一点？**（可多选）
- 重复数据积压 / 删除没人管 / 没真省下时间 / 跑完两眼一抹黑

### B 组 · 环境与约束

**4. 目标技术栈是什么语言/运行时？**（**决定候选池，必须问**）
- Python / Node.js·TypeScript / Go / Java（+ 其他自由输入）

**5. 目标存储 / 目标组件是哪一个？**（决定能不能走"稳定 ID + upsert"这类路径）
- Chroma / Milvus / Qdrant / pgvector（+ 其他自由输入）

**6. 数据从哪来？**（**最关键**：拿不到一次性完整清单则自动删除必须禁用）
- 本地目录 / 对象存储 / 数据库表 / 分页接口

**7. 要同步的内容是什么形态？**（决定要不要解析层）
- 已解析的 JSON/MD / PDF/Word / 混合格式 / 网页 HTML

**8. 规模与变化频率？**
- 几十份偶尔变 / 几百份每周变 / 上千份每天变 / 上万份持续变

**9. 做完后希望它怎么被触发？**（问目标状态，不是现状）
- 保持手工 / 接定时任务 / 服务里触发 / 先手工预留自动化

### C 组 · 边界与失败

**10. 源里删掉的内容，目标存储怎么处理？**（错一次就丢数据）
- 自动删（最干净）/ 先预览再删 / 只标记晚点再清 / 程序不删

**11. 跑到一半失败，希望怎么办？**
- 重跑一遍靠幂等 / 从断点继续 / 停下报错 / 跳过失败最后汇总

**12. 除正文外，还有哪些字段需要同步？**（决定要不要"只改元数据不重算"路径）
- 有权限字段 / 有描述字段无权限 / 只有正文 / 以后要加

**13. 这东西最终给谁用？**（决定严格程度）
- 自用 / 要给别人用 / 求职作品 / 上生产

## 三、其他需求类型（完整题库）

> 三类题库与数据同步域同规格：**每题带选项**，按 A（现状痛点）→ B（环境约束）→ C（边界失败）顺序问，
> **标「必须问」的题不可省**（漏问会直接废掉后续搜索或方案空间）。止损话术与一致性检查点见本文件 §四、§五，不重复。

### 检索 / RAG 优化类（10 题）

**A 组 · 现状与痛点**

**1. 现在检索最让你不满意的是哪种情况？**（可多选）
- 该找到的没召回 / 找回来了但排不到前面 / 材料都对但答非所问 / 质量还行但太慢

**2. 你有没有具体例子？**
- 随手能说出 1-2 个效果差的查询 / 大概记得是哪类问题 / 没有例子，只是整体感觉不行

**3. 现在怎么判断"效果好/差"的？**
- 凭感觉 / 攒了几个人工例子 / 有固定测试集和指标 / 完全没有参照

**B 组 · 环境与约束**

**4. 目标技术栈是什么语言/框架？**（**必须问**：决定候选池）
- Python（LangChain / LlamaIndex / 裸调） / Node.js·TypeScript / Go / Java

**5. 现在用的是哪套检索？**
- 纯向量 / BM25·关键词 / 混合＋融合 / 还没定

**6. 知识库规模与文档形态？**
- 几百份纯文本 / 几千份 PDF 为主 / 上万级＋多模态 / 其他

**7. 查询语言与形态？**
- 中文短问句 / 中英混合 / 长文档式查询 / 口语化、含错别字

**8. 向量库 / 检索引擎是哪个？**
- Chroma / Milvus / Qdrant / pgvector / ES 类 / 其他

**C 组 · 边界与失败**

**9. 效果提升到什么程度算达标？**
- 能答上就行 / 召回明显变好即可 / 要能量化对比（有基线跑分）

**10. 能不能接受"延迟上升换准确率"？**
- 可以（愿意加 Reranker 之类） / 不能（延迟敏感） / 分场景，高峰期不行

### 服务化 / 接口类（10 题）

**A 组 · 现状与痛点**

**1. 现在谁在用、怎么用？**
- 只有我自己跑脚本 / 团队几个人手工调 / 已有线上调用方 / 还没人用

**2. 有没有出过"多人同时用"或并发的问题？**
- 没遇到 / 有过冲突、超时或串数据 / 没测过，担心这个

**3. 现在最烦的是哪一步？**
- 每次改都要动代码 / 手动跑、忘了跑 / 结果没法看 / 出错没有任何提示

**B 组 · 环境与约束**

**4. 目标技术栈？**（**必须问**）
- Python（FastAPI / Flask） / Node.js / Go / Java

**5. 并发量与可接受响应时间？**
- 自己用，无所谓 / 小团队（<10 QPS，秒级可接受） / 对外服务（更高要求）

**6. 部署环境？**
- 本地 / 公司内网服务器 / 云主机 / 容器平台

**7. 要不要鉴权、要不要多租户隔离？**
- 不用 / 简单 token 即可 / 要按用户隔离数据

**C 组 · 边界与失败**

**8. 挂了怎么办？**
- 自动重试 / 降级返回兜底结果 / 直接报错 / 告警 + 人工介入

**9. 数据一致性要求到哪一级？**
- 最终一致可以 / 要强一致 / 单机场景无此问题

**10. 这东西最终给谁用？**（**决定严格程度**）
- 自用 / 要给别人用 / 求职作品 / 上生产

### 组合型任务类（多子机制，10 题）

> 判据：需求由**多个子机制**拼成（如"竖排古籍→横排+标点+坐标对照" = OCR + 标点 + 版面分析）。
> 这类需求的正确答案通常是"先拆子机制再逐个搜"（v1.5 实测结论），所以**第 5 题是全库最关键的定位题**。

**A 组 · 现状与痛点**

**1. 这个需求最终要达到的效果，能用一句话说清吗？**
- 能一句话说清 / 要说三句以上（很可能已是组合型） / 说不清，只知道大概方向

**2. 现在这活儿是人工做还是已有工具做？**
- 纯人工 / 有半自动工具 / 有现成流程但慢或不稳

**3. 整个流程里最耗人力的环节是哪个？**（**定位子机制的入口**）
- 输入解析（格式/OCR/清洗） / 转换处理（主体逻辑） / 结果校对 / 其他

**B 组 · 环境与约束**

**4. 目标技术栈？**（**必须问**）
- Python / Node.js·TypeScript / Go / Java / 不限（研究验证型）

**5. 能不能拆成几个独立步骤？大概是哪几步？**（**组合型任务的核心问题**：拆解粒度决定搜索策略）
- 能拆，步骤是…… / 大概能拆，但要试了才知道 / 拆不了，只能端到端交给一个模型

**6. 每个步骤的输入输出形态？**（决定子机制能否独立搜索）
- 都是标准格式（文本/图片/JSON） / 有自定义中间格式 / 还没想过

**7. 有没有可用的数据或已有模型？**
- 有标注数据 / 只有原始素材 / 什么都没有，从零开始

**C 组 · 边界与失败**

**8. 哪些步骤允许"差不多就行"，哪些绝不能错？**
- 转换环节可容错 / 关键环节要精确 / 全都要求高（需警惕）

**9. 允许跨语言 / 跨技术栈参考吗？**（组合型任务常跨语言命中）
- 允许，能用就行 / 最好同栈，降低移植成本 / 只接受 Python

**10. 预期是"能跑通的 demo"还是"要长期维护"？**
- demo，验证可行 / 要长期用 / 求职作品（兼顾可讲性）

### 数据处理 / 批任务类（10 题）

> 判据：需求的主机制是"一次处理一批数据"——即数据同步之外的批量转换／清洗／归并／计算（如"把 200 万条日志归并成会话""每天把 N 份单据批量转成结构化表"）。
> **第 4 题是全库同款必问项**（漏问技术栈 → 候选全部不可用）；**第 8 题是本域最关键的定位题**——重跑／断点续跑／幂等三选一，直接决定要不要建状态存储、以及失败恢复怎么设计。
> 本域题库原为骨架，已按 A/B/C 框架补齐；**尚未在真实需求上跑过**，首次用后回写教训。

**A 组 · 现状与痛点**

**1. 现在这活儿怎么跑的？由谁触发？**
- 手工跑脚本 / 定时任务自动跑 / 上游服务触发 / 还没有，正要建

**2. 现在跑一轮要多久？最耗时的是哪一步？**（**量级入口**：决定优化目标是算法、并行还是 IO）
- 分钟级 / 小时级 / 天级（须追问瓶颈在哪一步） / 还没跑过，说不准

**3. 现在的痛点具体是哪一点？**（可多选）
- 跑得太慢 / 一失败就得从头再来 / 数据变了不知道处理没处理 / 结果错了查不出是哪一步

**B 组 · 环境与约束**

**4. 目标技术栈是什么语言/运行时？**（**决定候选池，必须问**）
- Python / Node.js·TypeScript / Go / Java / Spark·Flink 等批处理框架（+ 其他自由输入）

**5. 数据量级、单条处理成本、能不能并行？**（决定单机还是分布式，以及值不值得做成本熔断）
- GB 级、单机跑得动 / TB 级、需要分布式 / 单条很贵（如调模型），必须先算成本 / 未知，需要先采样测

**6. 数据多久变一次、一次变多少？**（决定全量还是增量）
- 每天一次全量 / 小批增量、频繁到达 / 不定时来一大批 / 就一次，处理完不再变

**7. 失败重跑的代价（钱/时间）能承受吗？**
- 无所谓，重跑就是 / 贵，必须断点续跑 / 不能重跑（有不可逆副作用，如已发通知/已扣费）

**C 组 · 边界与失败**

**8. 中途失败是重跑还是断点续跑？**（**本域最关键**：决定要不要建状态存储）
- 全量重跑（接受重复劳动） / 断点续跑（要记录处理到哪） / 幂等重跑（重复执行结果不变）

**9. 处理结果的正确性怎么验证？**
- 抽样人工看 / 用规则断言（条数、字段、值域） / 有对照基线，能跑回归 / 还说不清（须在门禁 3 内定下来）

**10. 这东西最终给谁用？**（**决定严格程度**）
- 自用 / 要给别人用 / 求职作品 / 上生产

## 五、一致性检查的检查点

答案收集完后，逐项交叉核对：

| 检查项 | 典型矛盾 |
| --- | --- |
| **触发方式 vs 交付严格度** | "先手工跑" + "上生产"（后者通常要求自动化、监控、并发保护） |
| **数据来源 vs 删除策略** | "分页接口（拿不到完整清单）" + "自动删除"（**危险组合，必须改**） |
| **规模 vs 恢复方式** | "上万份" + "失败重跑一遍"（重跑成本可能不可接受） |
| **内容形态 vs 环境** | "混合格式 PDF" + "不要解析层"（矛盾） |
| **痛点 vs 明确不做** | 痛点是"删除没人管" + "程序不删"（矛盾） |
| **技术栈 vs 候选生态** | 需求是 Python，但已搜到的候选全是 JS/Ruby —— 说明**搜索轮次不够**，回到 L1 换关键词重搜，而不是将就 |
| **需求形状 vs 搜索策略** | 第 1 题答"要说三句以上／多个环节"（组合型），却仍按整块匹配搜 → **必须先拆子机制**（漏斗第 0 步），否则大概率 0 命中（v1.5 实测） |

**发现矛盾时的动作**：不要自行选择，把矛盾摊给用户裁决——**它往往决定复杂度天花板**。

## 六、交互硬要求（弹窗、叙事前提、样例先行）

- **必须用弹窗呈现，禁止把问题写成正文里的列表**。一个弹窗放 1–4 题（弹窗工具的上限就是 4），超过就分多个弹窗。实测：正文里列表式罗列 9 题用户一题未答；弹窗呈现的题全部作答；
- 每题带 2-4 个选项，把开放题改造成选择题；
- 显示进度（第 N / M 题）；
- 支持"改第 K 题"：维护答题表允许任意题重答，**重答后自动重跑一致性检查**（工具层无回退按钮，等价能力在对话层实现）；
- 跳过分两类：答"不知道" → 触发止损规则；答"暂时跳过" → 记为待补项，**门禁 1 关闭前必须清空**；
- **弹窗工具不可用时的降级**：改对话式——一次只问 1–2 题，等回答后再问下一批；**禁止**一次性把全部问题列成正文清单。实测的根因是单次认知负担过高，弹窗只是手段之一；
- **每道门禁题必须自带叙事前提**：不给场景就直接抛抽象选项（如"交付到哪一步""明确不做什么"的裸选项列表），需求方会读不懂——实测连续三轮弹窗被回"我没太明白你说的意思／这几个选择都缺乏叙事前提"。正确形态是**先给一句场景，再给选项**：
  > ❌ 差：`本次要做到哪一步？` 选项：`分块+字段结构 / 再加写入向量库 / 再加增量重算`
  > ✅ 好：`假设分块代码已经写好，你希望手里拿到的是哪一种？` 选项：`跑一条命令丢几份样例文档进去，打印出切好的块列表，你逐条看字段和切分对不对 / 在基础上块真的写进库，你能查到库里有多少条 / 文档改一版再跑一次，能看出新增·更新·未变分别是哪些块`
- **连续两轮被回"看不懂／缺前提"时的强制切换：样例先行**。停止追问，改**跑一个最小可运行样例给需求方看实物**（真实输出，不是示意图），再问"要／不要／改哪里"三选一。**原因**：需求方判断"实物对不对"的能力远高于"从抽象选项里联想出自己需要什么"的能力。

## 七、需求方不可达时的降级流程

触发条件：需求来自**公开材料**（issue / 论坛帖 / 项目文档）而**不是可对话的需求方**——没有任何人能回答门禁问题。

**不许**因此跳过 L0 直接开搜。按以下降级执行：

| 门禁 | 降级做法 | 产出物 |
| --- | --- | --- |
| 门 1 痛点与约束 | **三源推断**：① 需求材料**逐句提取事实**；② 需求所在仓库的现状（代码 / README 反推技术栈与形态）；③ **同主题历史 issue／讨论串**——一句话需求几乎总有前史。**③ 用哪个工具：`search_issues`（必须带 `owner` + `repo`）**——通用网页搜索与无范围 issue 搜索都不算这一源 | 推断版痛点清单，每条标 `[推断]` 或 `[假设]` |
| 门 2 方案选择 | **不做裁决**（无人可问）→ 改为"机制选项并列"：候选做法连同代价一起列出 | 方案选项表（并列、不裁决，全部 `[假设]`） |
| 门 3 需求规格 | 只写材料明确支持的 → 产出**最小可辩护规格** | 规格 + `[假设]` 清单（**必须逐条列出，不许静默**） |
| 一致性检查 | 降级为**自洽性检查**：`[假设]` 之间不得互相矛盾；矛盾项选保守解释并标注 | 矛盾项清单 |

> **信息量自检（开工前，尚未实测）**：三源补完后仍拿不出**至少一个可验收的诉求**时，**如实告知用户"该需求信息不足以支撑对标"**（走「找不到对标时怎么办」降级链的级别④——**借的是它"告知用户并停下"这个动作，不是它的语义**：级别④定义是"生态里无先例"，这里是"信息量不足"，**别把两件事混成一个编号**），**不要靠猜硬凑**。**两个触发条件同时成立时标哪个**：标**级别④**，并在同一行注明触发原因＝`信息量不足`——信息量不足是更前置的阻塞；反过来标"无先例"会把"需求没说清"包装成"业界没人做"。

🛑 STOP：交付物**首页（= §0 首行，紧随层级／档位声明之后）**必须声明"**需求方不可达，以下全部为假设**"，且 `[假设]` 清单作为 **§0 内的独立小节**逐条列出、置于 §0 最前面——让下游第一眼看到不确定性边界。**不写项数**（手写计数是第二处可矛盾的值）。**§0 内部的固定顺序（消除"先澄清还是先声明"的二选一）**：① 首行不可达声明 → ② `[假设]` 小节（**"若需求方可达、我会先问哪些问题"也写成 `[假设]` 条目**，不另开"澄清清单"小节）→ ③ 之后才是候选发现／降级裁决。这样"先澄清后搜"与"声明在前"同时成立。

## 八、提问语言规范 / 止损规则 / 一致性检查

### 提问语言规范

**门 2 之前只用需求方语言，禁止方案术语**（实测：用方案语言问，用户答"我不太明白什么意思"，该题直接作废）。

| ❌ 方案语言 | ✅ 需求方语言 |
| --- | --- |
| "权限变化时重算向量是浪费吗？" | "可见范围改了但正文没改时，你希不希望它为此重新算一遍？" |
| "解析失败的文档怎么处理？" | "有文件这次读不出内容时，库里原来那份该留着还是清掉？" |
| "验收标准是什么？" | "做出什么结果，你会觉得这时间和精力花得值？" |

**模糊需求里唯一确定的是痛点，不是设计。** 从痛点反推机制，比让对方凭空描述规格有效。

### 止损规则（防止变成拷问）

| 触发条件 | 动作 |
| --- | --- |
| **用户答成"目标行为"而不是"现状"**（实测：问"现在怎么做的"，答"不是该做增量吗、删除就该清掉"） | 把答复**记为该题的目标意向**，现状栏标 `[假设]`；**不要追问第 3 轮**——继续追只会拿到更多方案主张 |
| **用户答成反问／质疑**（实测："你为什么要全量呢"） | 视为对**产出物**的反驳而非回答。先自查产出物是否被误读（见门禁 1 的列名提醒），必要时重述后再确认 |
| 同一维度追问 2 轮仍无新信息 | 停止追问，给默认方案 + 理由，用户"不反对即通过" |
| 用户答"不知道／你看着办" | **立刻转选择题**——永远不让用户面对开放问题；**若用户是明确授权裁决（"哪种最稳你用那种"），则给出带证据的推荐并说明代价，再请其确认** |
| **总问题数达上限（见 SKILL.md 的 L0 止损规则，本行不重述数值）** | **必须**停止提问、强制收敛到门禁 3；未确认项标 `[假设]` 显式列出 |

### 一致性检查（门禁 1 与门禁 3 各跑一次）

交叉核对用户答案，输出三态：

| 结论 | 处理 |
| --- | --- |
| **一致** | 放行 |
| **有疑虑** | 标注 `[待确认]` 并列给用户裁决 |
| **矛盾** | **必须裁决后才能放行**——矛盾往往直接决定复杂度天花板 |

问题库（按需求类型预置的 L0 段门禁问题与选项）见 `references/l0-question-bank.md`。


## 九、交互硬要求（原文）

把开放题改造成选择题，并显示进度（第 N / M 题）。

**连续两轮被回「看不懂／缺前提」时强制切换样例先行**：停止追问，改跑一个最小可运行样例给需求方看实物

## 十、三道门禁的呈现提醒与「门禁 1 之前先读本地代码」（原文）

> **门禁 1 的列名提醒**：「现在怎么绕」这一列容易被需求方读成"你在提的方案"（实测：连续两次被当成提案反驳）。
> 呈现清单时**显式声明"右两列描述的是现状，不是我的提案"**。

> **门禁 2 的正交性**：若存在**多个互相独立**的机制维度（实测：变更识别粒度 vs 失败安全是正交的，
> 可以"块级粒度 + 整代切换"也可以"篇级 + 事务更新"），**必须逐个分别问**。合成一个问题会让用户
> 只能选到其中一维，另一维被静默默认。

> **门禁 3 的收敛要求**：约束前提里的技术选型（如"向量和台账存哪"）若用户答"还没定"，**必须在门禁 3 内
> 收敛**，不能漏到门禁 4 —— 它会直接决定门禁 4 能裁决什么（实测：存储未定会让"失败安全"的裁决悬空：
> 跨系统就做不到真原子提交）。


> **门禁 1 之前先做一步：判"需求所在的系统是不是就在手边"**。工作区／已有仓库／已上线代码常常**就是**那个目标系统——在本地就**先读它的相关代码**（检索入口、权限过滤、写入路径），再去 L1 找对标。两个收益都实测过：①能给出精确接入点，而不是停在抽象层；②**能发现由本地代码决定的最高危风险**——实测：本仓库的权限过滤施加在**检索函数内部**（`knowledge_base.py:1061` 的 `filter={f"allow_{role}": True}`，缺该键的 chunk 不进入候选集），于是能**推出**一条必须提前写成设计约束的风险：**任何加在检索之上的缓存都会绕过这层过滤**——缓存键不含 `role` 时，HR 命中过的答案会漏给员工（**越权泄漏**）。⚠️ 这一条是**推断，不是实测**：当前代码里没有答案级缓存，所以它该被写进 §0 风险表并要求"缓存键必须含 role"，而不是被当成"已发生的泄漏"。**把推断写成实测，正是本 skill 最反对的那件事。****不做这一步的后果不是"少一点背景"，是把最严重的那条风险漏掉。**
